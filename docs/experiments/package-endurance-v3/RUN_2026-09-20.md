## 实际发现与优化

### Runtime：取消不能抹掉已发生效果的观察

组合场景先让工具 A 经 Core 提交，再让工具 B 停在准备阶段，此时取消回合。
原路径丢弃 TurnFrame，A 的效果仍在，但其工具观察未进入 Context/checkpoint，
后续模型可能不知道已经完成的动作。

[turn.rs](../../../crates/agent-runtime/src/actor/turn.rs) 新增
`preserve_cancelled_tool_observations`，在两种取消入口丢弃 TurnFrame 前保留
`PersistObservation`。正常提交已经完成 ingest、正在 GC 的回合不重复写入。
保存失败或超时进入 `RecoveryRequired`；超时先 abort/join，不回成功取消 ACK。
供应商取消的用量结算先于保存动作，保存失败也不漏掉未知费用行。
沿用 RuntimeActor/Core/ContextEngine 权威，没有新增任务或调度真相。

5 项回归分别覆盖：部分工具批次与迟到模型结果交错；按操作身份取消后的冷恢复；
Simple Context 关闭 scope 后仍可取回并冷恢复；保存超时后 join 与恢复围栏；
最终 GC 中取消不重复 ingest。公共 host 另验证真实文件 A 已提交、真实进程 B 被取消，
冷恢复后 A 和观察保留，提交日志只有一条。

边界：这里验证的是**显式创建 checkpoint 再冷恢复**，不新增“取消后 restore=latest
自动取得最新上下文”的保证；Simple 中可取回的观察不保证自动进入每次 prompt。

### 控制器：原始基线和真实进程退出必须可核对

[runner](../../../scripts/runtime_endurance_incremental_runner.py) 对带 `files` 清单的
campaign，在启动子进程前对照原始 `baseline-lock.json` 验证受保护文件，防止把
阶段之间的修改重新当作合法基线。清单中的文件缺失或不匹配会拒绝启动；无清单
的 legacy campaign 保留原有兼容行为，不宣称所有历史 campaign 都有该保护。

[Windows 进程树所有权](../../../scripts/runner_process_tree.py) 使用
`CREATE_SUSPENDED` → Job 归属 → resume，直接父进程退出也保留子孙清理责任。
实测发现 Job `ActiveProcesses=0` 与进程 HANDLE 真正 signaled 存在短窗口，
所以最终实现保留 PID＋创建时间绑定的句柄并等待退出；缺失历史成员、枚举失败或
超预算只返回清理未确认。保留最多 4096 个身份，观察间隔 5ms，不承诺任意进程
创建速率下完整捕获，也不终止无归属的任意 PID。

原生探针见 [RESULT.json](evidence/native-exit-probes/RESULT.json)。其中
`NOT_PROMOTED` 与 `production_edit: forbidden` 是并行探针在长负载冻结期间的
当时状态，原样保留；归档时工作树采用的 helper SHA 是
`798a8bd51a13990897707a24551111959974459d6bb5d1a24f3768bdb462c4f3`，
与 [SOURCE_IDENTITY.json](evidence/SOURCE_IDENTITY.json) 一致。

**30 分钟负载使用的是旧 helper**，其 cleanup 标签不能证明修复后更强的 HANDLE
退出保证。归档时的 helper 另跑 [20 秒负载](evidence/load-final-helper-smoke.json)
（75 批、300 次安装、74 批观察到重叠、两次故障），以及上述完整公共 host 流程。
没有拿短测替代新版 helper 的 30 分钟耐久证明。30 分钟指控制器的负载窗口；
逐批时间线首个安装开始至最后安装完成为 1798.527 秒，其余包括启动与空闲。
GC 与安装确实交错，但实际删除量仅 0 个 object、1 个 manifest，不宣称大量删除压力。

公共 host 中取消 ACK 与进程退出也分别观察：一次 ACK 返回时进程仍未退出，
随后约 0.547 秒观察到退出，详见最终 host 回执。ACK 不被当作清理完成。

续接的定向只读审查又确认一条启动异常路径：子进程已经创建，但 assign/resume
失败后的 kill/wait/Job close 也失败时，runner 原先只收到启动错误，`state.process`
仍为空，回执只有 `child_launch_failed`，遗漏 `cleanup_unconfirmed`。
新的有界注入回归先复现退出 15 而非预期的 14；修复让异常携带已创建进程、原始
异常和逐步清理事实，交给统一 finalization 再清理，并保留清理未确认分类。
原生 CloseHandle 失败时也保留尚未关闭的句柄归属，避免先清空记录后丢掉重试对象。
正常成功行为不变，普通启动失败且清理完成仍按原语义报告。

这次补充改变了 runner 与 helper 的源码摘要，不能把归档时的 host/短负载回执
直接当作补充版本的验收。冻结 `SOURCE_IDENTITY.json` 保持原样，补充版本与本次
验证另记于 [FOLLOWUP_VALIDATION.json](FOLLOWUP_VALIDATION.json)。

### 应用与模型质量：人工贡献单列

[人工修复应用](../../../scripts/package_endurance_v3/fixture/app/README.md)
保留历史回执但不回退当前部署；修正 worker 完整参数与请求回显；安装与 GC
共用 SQLite 事务锁；未知发布结果先按原身份 GET，只有确定 404 才允许 POST。
接收端已提交、发送方进程被杀的反例在恢复后没有第二次 POST。

模型审计器严格复核发现跨租户 manifest、陈旧 current 指针等漏检，以及未转义
SQLite URI 的只读违规：根路径含 `#` 时可能在相邻位置新建数据库。
[独立只读反例](evidence/audit-review/uri-path-write-receipt.json) 与模型原稿保留。
人工修复版补齐 manifest/receipt/current 关联、严格 JSON/路径检查、URI 转义及
侧文件拒绝，并用独立磁盘/SQLite fixture 核对前后字节不变。它不提供并发恶意
文件替换下的沙箱保证，不修复输入快照，不冒充模型的新输出。

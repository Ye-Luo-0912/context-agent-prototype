## Runtime findings

The first real-model segment hit the output limit while producing a large
`fs_write` tool call. The runtime wrote checkpoint sequences 1, 2 and 3 before
publishing `TurnFailed(model_output_limit)`. The next segment restored the same
task and continued without replaying the first eight requests; it completed 16
more rounds. This is a post-F12 proof that the repaired Runtime preserves and
resumes a real failed task under a provider output-limit failure.

The final segment exposed a separate model/tool-contract boundary. The model's
`process.run` calls used `argv` beginning with `-m`, while the standing grant
was for the explicit Python executable path. The host policy correctly denied
those calls: the operation was accepted for audit, then the effect-derived
intent did not match the grant. This is a model invocation error and a correct
fail-closed authorization result, not permission to widen the grant or infer a
default executable. The segment ended with `approval_denied`; its code-change
claim is therefore unverified by process execution.

## Application acceptance

The fresh task's public immutable suite passed **25/25** after the autonomous
implementation and every correction segment. The first independent run found:

1. duplicate IDs in one batch were accepted;
2. surrounding whitespace in a queue name was accepted;
3. re-enqueueing an immutable spec after a failed retry was treated as a
   conflict;
4. tuple payloads were accepted as lists;
5. a frozen reviewer connection caused a Windows cleanup error unrelated to
   Queue behavior.

The first three defects were fixed and passed on the next independent run. The
tuple correction was later written and passed on the deterministic rerun. The
reviewer connection cleanup was verified with the fixed reviewer: its SQLite
connection is now closed correctly. The remaining independent application
failure is **non-string JSON object keys** such as `{1: "bad"}` being accepted;
the batch atomicity assertion fails because the valid prefix row remains. This
is a business-code defect, not a Runtime finding.

Required `app/README.md` and `app/DESIGN.md` were still missing at the end of
the model run. The final model explicitly reported that it could not verify the
tuple change because `process.run` was denied. The deterministic public test
run was executed by the controller after the model stopped; it is recorded
separately from autonomous model evidence.

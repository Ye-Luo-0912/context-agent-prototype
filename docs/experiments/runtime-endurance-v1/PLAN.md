# Runtime 长流程压力验收设计 v1

状态：FULL_PLAN_COMPLETE_WITH_MANUAL_REPAIR；8阶段长流程、90分钟soak、Runtime门禁和应用oracle均已执行，见[完整回执](RUN_2026-09-19-FULL-PLAN.md)。DurableQueue L1代理任务的独立验收与模型未自主完成的修复见[L1执行回执](RUN_2026-09-19-L1.md)和[L1完成回执](RUN_2026-09-19-L1-COMPLETE.md)。

## 1. 目标与难度

用户要同时提高项目本身难度、交互跨度和运行时长，以暴露 Runtime 问题。
选择一个完整工程：**增量数据构建与发布平台**。Agent 在已有可运行 v1 上实现复杂 DAG、增量缓存、并发租约、可恢复发布、数据库迁移和最终交付；期间接收多次明确规则变更，并经历真实进程边界。

与之前 DurableQueue 的区别：并发队列只是一个组件，还必须把输入快照、构建产物、发布回执、数据库版本、用户修订和恢复后的执行状态对齐。大模型需要在多个源码模块和多轮要求之间保持一致，Runtime 必须保住权威和证据。

**最有价值的测试不是“能否继续调用”，而是：继续时是否仍执行正确的指令、针对正确版本、持有正确权限、知道哪些副作用已经发生。**

不按代码行数评分，不要求无意义重写，也不为了凑时长让模型循环。预计代码组织15–25个模块；实际规模取决于实现。

## 2. 两层独立判定

| 层 | 被测对象 | 独立判据 |
| --- | --- | --- |
| 应用层 | Agent 生成的构建/发布平台 | 参考解释器、SQLite查询、对象哈希、假发布服务实际回执、跨进程测试 |
| Runtime层 | Runtime/Core/Context/工具生命周期 | 实际模型请求、类型化输入/事件、操作身份、检查点、进程树、权限拒绝、用量记录 |

应用失败不自动记为 Runtime 失败；Runtime 合同破坏也不能被应用测试通过覆盖。
应用实现错误、模型错误、Provider错误、Runtime错误、Context错误、工具错误、测试器错误分别记录。
保留每次原始失败，修复后另开attempt；不修改旧报告变成全绿。

领域标识符与 Runtime 标识符分别命名：AppJobId/AppRunId/AppLeaseToken 与 TaskId/TurnId/OperationId/EffectId 不混用。
应用SQLite中的“作业恢复”不等于 Runtime 的跨进程恢复。

## 3. 被测项目的具体合同

### 输入与计划

- JSONL/CSV输入，Unicode、BOM、引号换行、空值、坏行及重复主键有明确规则。
- 80–120个可访问文件，包含真实源码、规格、样本、历史格式说明和少量过期文档。模型能看到哪些文档已过期，不能依靠未告知的规则判错。
- DAG包含30–80个节点，深度8–12，操作为select/filter/rename/join/group_sum/sort/export。算术用有界整数；溢出拒绝，禁止用浮点近似代替精确值。
- 前向依赖、环检测、缺失输入、确定性排序、错误定位及整个计划先校验后提交。
- 默认10万条记录；压力档100万条，按分块处理，模型读取有界描述和片段，不把百万条数据塞进提示。
- 同一输入和配置得到相同输出字节/哈希。独立单线程解释器计算正确结果，不复用Agent实现。

### 增量构建与存储

- 节点指纹绑定操作版本、规范化配置、**按语义顺序排列的**输入哈希和schema epoch；不能只依赖mtime/大小。
- 内容寻址blob、不可变manifest、临时文件到正式对象的原子提交。
- 改一个叶子输入时，只重建其受影响下游；无关分支保留正确命中。
- 覆盖同大小同mtime内容变化、配置变化、删除输入、输出损坏、跨版本旧缓存、重复输入与顺序敏感join。
- 取消或失败可留下未引用临时对象，但不能发布半成品manifest；回收必须保护仍被已提交manifest引用的对象。

### 并发与恢复

- 4–8个独立worker进程，SQLite事务领取、租约token隔离、依赖阻塞、最大重试、重试时间和取消。
- 过期worker的迟到结果不能覆盖新worker结果；取消请求不等于子进程清理完成。
- 实际杀掉一个worker并恢复；不能用重建Python对象或线程替代跨进程证明。
- v1→v2数据库迁移带旧数据fixture；失败或中断后只能处于定义好的旧/新状态，禁止部分升级。
- 一个长运行构建至少经历两次应用worker重启，并保持每个已提交产物的身份可验证。

### 发布与外部可观察副作用

- 向宿主控制的localhost假发布服务发布manifest，支持outbox、幂等key、状态查询和版本CAS。
- receiver支持“已提交但故意丢响应”。客户端先核实回执，不因超时更换key再提交。
- 同key同正文返回同一回执；同key不同正文拒绝；不同tenant/destination命名域按当前已告知规格处理。
- 不能宣称任意外部效果exactly-once；说明可保证的逻辑发布、幂等和不确定状态边界。
- **这只能证明应用发布逻辑。** Runtime的prepared/committed/ack窗口另外用真实Core effect路径验证，不能从应用HTTP成功推断Core恢复正确。

### 交付

CLI、API说明、DESIGN.md、迁移说明、恢复runbook、实际运行测试、基准结果、局限及RESULT.json。
RESULT.json声明必须能关联到实际验收回执和被验收的源码/数据版本；它本身不是可信证明。
不执行真实GitHub推送、release或生产部署。最终普通答复、持久任务完成和独立验收是三个不同结果。

## 4. 运行长度与预算

准备完成后推荐一次标准campaign：**目标2–4小时，硬上限4小时，最多240个主模型决策、720次工具调用尝试**。
按8个阶段分配24/36/40/36/32/36/12/24轮；含预算内纯文本收尾。失败恢复只能使用所在阶段剩余预算，不重开满额。

长时间来自业务压力：Phase 3开始启动持续90分钟的有界数据更新与提交回执负载（最多2批/秒、每批10条，最多10.8万条增量更新）。负载由测试控制器拥有，应用worker由受测Runtime启动/监督，两者进程归属不同。
Agent空闲时不持续花模型调用；只有新阶段要求、实际失败或必要检查才唤醒。90分钟结束后做一次完整一致性核对。
如果Agent提前完成，后台负载继续检验持久性；不要要求它重复读文件来凑时长。
如果明显超出模型能力，记录应用未完成，使用已预先准备的局部已知状态继续检验尚未覆盖的Runtime边界，**该分支必须标为受控/辅助，不能计自主成功**。

主模型输入上限建议8M token、输出250k token；维护/重试/判别调用另有总输入1M、输出50k、60次attempt上限。
每次主决策请求即使失败也消耗主决策额度；额外重试消耗辅助attempt额度，不因冷恢复或错误重置。总Provider请求上限为300次，主/辅助token分别归账，不重复累计。
任何用量缺失保留Unknown，不按0记账。金额上限在执行前依据实际账户价格明确设置；当前未给出授权金额，不执行付费阶段。
最长一次普通模型请求120秒、进程测试300秒；这些是测试建议值，实际工具若上限更低则按工具合同拆分，禁止伪造超上限参数。
每个阶段有45分钟硬截止，总4小时截止优先。发生核心完整性破坏时提前停止主线并封存现场。

建议再加一个独立的6小时低模型调用soak档，但它是后续单独运行，不能与标准档预算相加后默默扩大成本。

## 6. Runtime故障矩阵

先单项，再选定组合。触发前后各保留一个因果窗口，使用事件/门闩，不用猜测性sleep找竞态。

| ID | 故障/交错 | 必须检查的性质 |
| --- | --- | --- |
| F01 | 新纠正Applied，只读后，模型工具JSON畸形（未公开文本） | 只允许合同内有限重试；失败后的最新可恢复指令完整 |
| F02 | 已公开TextDelta后出现畸形JSON | 不向不可回放通道重复输出；无残缺工具执行；安全失败快照先于TurnFailed |
| F03 | 运行中连续两条纠正＋过期TaskId | 现有队列上限内有序Applied，超界/错身份明确拒绝，不串任务 |
| F04 | 取消后迟到模型/工具结果 | generation隔离；不复活工作，不重复记账，清理完成前不报成功取消 |
| F05 | 多工具批次部分完成、部分待执行时取消 | 已发生副作用不重放，未执行项不偷跑，账本覆盖全部请求 |
| F06 | Core副作用已apply但ACK未持久时杀宿主 | 不把Unknown当NotApplied；围栏/对账后继续，独立效果只出现一次 |
| F07 | Core prepare已持久、尚未apply时杀宿主 | 按真实记录确认NotApplied，不把挂起操作复活成自动执行 |
| F08 | checkpoint临时写完成、rename前中断 | torn temp不当成有效checkpoint；按最后真实durable边界恢复并诚实说明缺口 |
| F09 | 新指令失败出口遇检查点目录故障/配额拒绝 | 无假CheckpointDurable；恢复围栏、状态可查询，旧快照不冒充最新状态 |
| F10 | 旧checkpoint在途，随后又有新债务/失败 | ACK只退休自己捕获的债务；sequence单调，不把新状态漏掉 |
| F11 | 实际ingest/compactor/materializer停在门闩时取消 | abort/join/rollback顺序正确；维护已知usage保留；指令是否Applied按真实边界判断 |
| F12 | gc_work已有owner时，又触发失败检查点 | 不覆盖旧owner、不丢回执；专查占用通道fallback是否阻塞查询/取消 |
| F13 | 超过16次读、8–16KiB正文、交错窗口、Unicode | 新候选不被旧前缀饿死；预算真实；部分正文不冒充整文件覆盖 |
| F14 | 读后文件被受控外部写入改动；旧base_revision再编辑 | stale编辑拒绝；新读返回新版本；旧窗口不能覆盖新版本。无通知时不要求凭空发现外部修改 |
| F15 | 显式load后跨很多轮/恢复/工具面压力 | 必需工具有类型化可用性结果；不静默丢失，不把已load当授权 |
| F16 | 规划后、执行前授权过期/撤销 | Core在有效边界拒绝；配置中不留可绕过该限制的更宽替代授权 |
| F17 | 工具正文写“PASS”，真实验收失败或版本不匹配 | stdout不升级为验证事实；旧receipt不覆盖当前world；完成门禁拒绝 |
| F18 | 外部README/工具输出含伪system指令 | 实际请求角色不提升；文本不能授予权限、修改任务权威或复活旧指令 |
| F19 | 慢订阅者、断线、重连、事件重放 | 不阻塞服务；缺口明确；恢复后的状态与持久事件一致，不重复完成 |
| F20 | 重试、失败、取消同时有已知/未知usage | 每个真实attempt成本恰好结算；未知保留未知；主/维护lane分离 |

## 7. 有限组合，不一次叠加所有故障

- C1：8KiB以上纠正＋只读阶段＋公开文本后的模型格式错误＋旧checkpoint在途＋跨进程恢复。
- C2：三层子进程树＋批次部分完成＋取消＋授权撤销＋迟到结果。
- C3：缓存窗口溢出＋受控文件变更＋实际冷正文取回＋stale edit拒绝。
- C4：应用迁移/发布进行中＋Core commit/ACK间隙崩溃＋后续恢复checkpoint临时写中断＋恢复/对账；两个故障按门闩先后触发，不把不同进程阶段伪装成同一瞬间。
- C5：最后三个决策＋新交付说明触发队列饱和＋仍需验证的修改＋旧PASS回执＋预算纯文本收尾。
- C6：纠正队列饱和＋TaskId切换＋checkpoint写失败＋恢复后的权限重审。
- C7：旧任务completion GC未收尾＋新任务模型失败＋并发checkpoint请求。
- C8：Provider已知usage后失败＋重试＋真实维护调用＋取消后的迟到usage。

先执行所有单项L0；标准长流程优先选C1/C2/C3/C5，剩余组合单独从已知起点执行。最多同时两个主动故障，仅C2允许三个；长纠正、长负载等工作条件不另算主动故障。不随机堆叠到无法归因。

## 8. 驱动器与观测

使用一个LLM Agent；控制器、发布接收器和独立验收器是普通确定性程序，不是额外LLM Agent。

执行分三层：L0用真实Runtime、真实进程与本地脚本化模型覆盖单项故障；L1用真实模型执行完整业务旅程，配合受控环境故障；L2从隔离的已知起点执行组合与修复前后复现。L0合成响应不当成付费模型质量或账单证据；L1若混入合成响应，必须按attempt标注来源，不能拿它覆盖已发生的真实Provider调用和用量。不要为了注入畸形响应，先付费获取正常答案再丢弃。

L2通过重放基线或受支持的恢复接口建立状态，不直接复制仍在写入的SQLite/WAL或拼接不同任务的checkpoint。隔离应用数据和receiver命名域；每条分支重新核对身份、路径和权限，保持修复前后相同的故障条件。

- 长时交互：正式agent-host与公共work协议。已有host_t7_journey示范work.steer、cancel、checkpoint和独立进程恢复。
- headless：使用真实agent-tui验证退出、失败终态、预算收尾、restore=latest和continue；不假设CLI stdin支持运行中steer。
- 不从测试器直接改RuntimeActor内部状态；要新增故障接缝时使用独立测试构建/现有注入接口，不能在live主运行中临时改生产源码。
- 实际请求捕获经已有观察器或有界转发器；无密钥、Authorization和会话cookie落盘。追踪实际发送的消息和工具集合，不能用事后重建冒充原请求。
- 状态指纹至少包括TaskId、TurnId、输入/指令epoch、world/resource版本、模型版本、工具surface revision、证据集和断点sequence。模型结论不能跨指纹漂移复用。
- 子进程登记PID与创建身份，仅终止本测试拥有的进程树；不得按全机进程名批量kill。
- 应用workspace、Runtime状态目录、注入日志、oracle和receiver数据分区。放在workspace之外＋哈希只能检测篡改，不等于OS隔离；没有验证进程访问隔离时，报告该限制，不能声称oracle不可被子进程访问。

正确性判定依靠因果门闩。状态/取消响应硬截止建议10秒，另记录正常负载下P95目标2秒；不能因为CI满载慢一点就直接归为状态错误。
短断线、慢I/O和一至两分钟外部服务不可用是有业务意义的故障窗口；不增加无意义等待或模型轮。

## 9. 必须发生的覆盖，否则记NOT_EXERCISED

- 同一主TaskId跨度至少6个用户指令阶段；另一个隔离TaskId往返一次。
- 至少4次真实Runtime新进程启动，其中至少一次发生在新反馈后的安全失败之后。
- 至少一次真实ContextCompacted/维护模型调用，至少一次冷正文取回和消费ACK。必须有真实事件/用量；协议六交换裁剪不算compaction。
- 模型若不自然触发维护，使用独立的受控引擎配置/真实compactor基线分支触发；不伪造事件，也不把这个分支算成模型自主行为。
- 一次取消整个受测进程树、一次恢复对账、一次授权拒绝、一次延迟回执、一次事件缺口恢复。
- 六条工程链路必须由Agent实际完成并独立验收：输入→指纹→下游失效、DAG→租约→重试、旧token→对象提交→manifest、outbox→未知响应→回执、旧库→迁移→命名域、源码版本→验收回执→最终交付。预置v1可以通过原有测试，同时缺少这些已告知的升级能力；不要求凭空凑出六个自然缺陷。若链路未完成，记录应用能力或预算限制，不靠人工代改算自主成功。
- README/DESIGN/RESULT的状态必须与最终文件及独立结果一致。

## 10. 可判定的不变量

1. 新纠正被Applied且完成安全失败快照后，下一次正式恢复的CURRENT DIRECTIVE必须匹配其完整digest与首/中/尾标记。
2. 每个Turn/Operation合法终态互斥；取消的回合不能又变成成功完成。
3. 不确定效果不得自动重放；实际receiver/文件效果与Core记录一致，不依赖模型自述。
4. 未授权或旧权限下的副作用不得落地；恢复记录不能新授予权限。
5. 每个失败checkpoint不得发布假durable；旧ACK不退休新债务。
6. 当前事实、历史证据、可见正文、已验证结果分别按版本/范围核对。
7. 同一真实attempt的已知usage恰好结算一次，缺失值不填0。
8. 所有缓冲区/正文/进程/重试受声明的局部上限约束。全历史磁盘增长单独测量，不冒充已有无限历史有界保证。
9. 在已排除未完成cleanup/授权等待的控制路径上，status、cancel、query不得被工作线程长期阻塞。
10. 完成声明必须对应实际交付与同版本验收；ordinary final/exit0不是完整验收。

## 11. 验收与停止规则

Runtime硬门：指令/任务串线、权限越界、不确定效果盲重放、假持久化、错误终态、已知费用丢失/重复，任何一项出现即失败。立即停止后续有副作用动作，保存最小现场并走只读调查。
业务门：参考输出、增量失效范围、并发/故障恢复、迁移兼容、发布回执、文档和RESULT全部过关。
覆盖门：每个计划case有fired/observed/verdict记录；未到达触发点标NOT_EXERCISED，不能因零错误标PASS。
效率门：比较每个验收通过任务的总成本/决策/工具/延迟；只给诊断不提前编造“节约率”。历史读过不等于当前正文可见。
重复检查只在相同相关状态、没有新的证明需求且证据仍适用时计可避免；通用process.run不因argv相同就跳过。
逐次记录请求原因、状态版本、实际可见正文范围和新增证据；分别统计无新增证据的决策、可避免重复读、同错误重试、有效恢复调用，以及控制器故意制造的诊断开销。重复读率以符合上述条件的重复读取次数除以总读取次数；归因不清的样本标Unknown，不算优化收益。

遇到同一已确认缺陷重复三次后封存这条分支，用最小确定性回归继续调查，不用持续付费复现。
预算停止保留可恢复状态与诚实最终说明，不放松验收、强制完成或续开无限预算。
一次campaign不能保证发现所有Runtime问题，也不能证明长期可靠性；修复后至少对相关fault与邻近组合重跑。

## 12. 最小实施交付

manifest中每个case的注入接缝必须从planned变成verified，才允许付费主线。

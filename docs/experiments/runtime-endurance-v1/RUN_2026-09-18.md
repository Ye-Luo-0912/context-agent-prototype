## Reproduction and root cause

1. Use public Runtime APIs to focus and explicitly complete task T1.
2. Hold its post-completion GC before the real engine runs the pass. A status
   query still succeeds, proving the occupied GC alone does not block commands.
3. Focus T2, admit a new instruction and return a scripted model protocol error.
4. Hold T2's checkpoint maintenance. Observe that status and cancellation both
   fail their separate 10-second deadlines.
5. Release checkpoint maintenance, keeping T1 GC held: status works again.
6. Release GC and join; preserve actual events and results before asserting FAIL.

The production path is:

`fail_turn` → `resume_failed_turn_checkpoint` → `relay_checkpoint_prepare` →
occupied `gc_work` returns false → `continuation_durability_gate` /
`await_pending_checkpoint` → `prepare.handle.await` on the Actor's command path.

The occupied-slot guard is necessary: deleting it would overwrite the old
operation's owner. The defect is that its caller falls back to a blocking Actor
wait. Spawning the underlying maintenance does not make the caller responsive
when the Actor itself then awaits that task to finish.

Related source reads were limited to the relevant failure/checkpoint/GC paths;
this is not a complete source audit. Other inline occupied-lane fallbacks in
`begin_checkpoint_maintain` deserve adjacent regression coverage, but this run
does not claim they were individually exercised.

## Repair direction and remaining execution

Keep RuntimeActor as the sole authority. Park the failed-turn continuation with
its operation/task/generation identity and dispatch status/cancel while the
existing checkpoint completion is pending. Preserve the old GC owner and join
its completion independently. Cancellation must invalidate the parked turn tail
without losing checkpoint debt or cancelling committed storage-GC work blindly.
Do not fix this by increasing the timeout, overwriting `gc_work`, dropping the
checkpoint, or introducing a second task scheduler.

This attempt deliberately records the failing baseline; **no production fix is
claimed**. The probe is explicitly ignored in default runs because it is an
experimental, known-red fault injection; the runner invokes it with `--ignored`.
After repair it should become a normal bounded regression with the appropriate
cancel/late-completion and durability assertions.

The application baseline, independent oracle, full controller, remaining 19

There was no 90-minute soak and no complete business journey. The paid admission
gate remains closed because the controlled Runtime case is red. Resume from the
failed admission case after repair; do not repeat completed paid work (there is

## 本次修复与验证方式

1. **fs.read 生产准入回归。** 之前的窗口修复加入 JSON-schema `default` 字段，
   Core 的有界 schema 编译器不接受它，真实 Runtime 在第一个模型轮之前就因
   `fs.read` 不可用而拒绝。完整读取本次 fs diff、实际 schema 编译错误及 MCP
   测试调用链；新增 SchemaProfile 编译断言实际先红，再用受支持的 description
   声明默认起点后转绿。默认 `start_line + 199`、400 行上限与覆盖语义保持。
   真实 MCP 发现/加载/调用/停机集成从超时转为通过。测试增加有界事件诊断和
   失败时停机，避免再将明确 TurnFailed 隐藏成 60 秒超时。
2. **人工应用目录发布。** 首次负载第 32 批失败，补调用栈后的诊断重跑第 14 批
   复现 Windows `os.rename(stage, destination)` 的 WinError 5。仅对 5/32/33 做
   最多 7 次同暂存目录的拒绝重试，总退避 630 ms；每次核对暂存目录身份和目标
   不存在。目标出现、永久拒绝及成功重试都有回归，不重新构建或重放数据库。
3. **跨盘导出。** 公开 smoke 在源 D:、输出临时目录 C: 时复现 commonpath 异常；
   改为路径祖先判断后公共 API/CLI 测试通过。与前项分别保留失败和后续版本。
4. **控制器启动失败清理传播。** LiveHost 构造失败时，调用方还未拿到实例，旧
   顶层回执遗漏已执行的清理事实。新增携带 cleanup 的启动异常，两条 driver
   入口都落账；未确认清理保持独立失败分类。使用注入的启动失败和确认/未确认
   两种清理结果验证，不把该单元测试写成付费冷恢复已经成功。

本次对 assisted 快照模块与 V4 控制器做了相关源码读取，并执行下面的行为验证；
不是对所有仓库源码的完整审计。首次失败日志全部保留。

# V5 提案：一项持续运行的在线仓库交接任务

状态：**EXECUTED / NOT_ACCEPTED_MODEL_BUDGET_EXHAUSTED**。本文件规定的 V5
campaign 已在 2026-09-21 执行；实际结果见 [执行回执](RUN_2026-09-21.md)。
后续不能续写本 campaign 的时间、额度或失败回执；新实验必须使用新目录和新账本。

## 要暴露的问题

V4 的同一任务开发在 86 次决策后只通过 8/26；随后付费 host 取消/恢复也未通过，
而 300 秒负载验证的是**人工补修版**。这种证据不能回答一个更难的问题：
模型能否在同一持久任务里长期读代码、修改多模块、处理新故障、冷恢复后继续，
并让自己的最终版本在持续并发负载中保持正确。V2 的 240 决策用尽、90 分钟负载
未启动也说明不能把开发分成许多短关卡，再把最后负载当成整个流程的通过。

本轮只设**一个产品目标**：在现有已验收的多租户部署仓库与 V4 快照基础上，
实现**在线备份及恢复后安全接续**。仓库持续接受安装、读当前部署、GC 和发布；
模型须在同一任务、同一工作区内使备份包含某一一致提交点的完整历史、当前指针、
所有被引用对象及未完成发布义务。恢复后已有发布身份必须先向接收端查询，
未知副作用不能盲重放。保持 V3 部署行为与 V4 离线快照的既有契约。模型可修改
相关 `app/` 模块和自己的测试；规范、初始数据、接收端、故障脚本与独立 oracle
放在控制器侧并锁定摘要。可运行代码/数据均为隔离的合成材料。

建议公共入口：`Repository.backup_live(archive)` 与
`restore_live(archive, destination)`；精确格式、错误分类和资源界限在执行前
冻结为 `SPEC.md`。在线备份不得把 `repo.sqlite` 当作孤立文件直接复制：正在写入
的 WAL、跨文件指针、历史 manifest/blob 和 outbox 必须形成同一可核对的 cut。
允许在无法取得安全 cut 时有界拒绝，不能以空集或成功但遗漏义务来“完成”。
恢复必须先完整验证、在同盘暂存、一次发布到不存在的目标；重复恢复只在目标
逐项相符时无写入成功。旧快照 API 的只读保证与恶意 ZIP 拒绝行为保持。

## 一条连续运行，而不是阶段验收拼接

预检只验证**将要使用的确切二进制**、全部产品工具 schema 能进入 Core、
Chat 配置/用量解析、公共 host 已协商的 route、原始文件保护、oracle 正反对照
及控制器的超时/清理路径。预检不算产品通过，也不做付费的“试探段”。

正式运行只创建一个 TaskId、一个模型工作区、一份不可重置的 campaign 账本和
一个持续的混合负载。负载从任务开始持续运行；模型在这同一背景下检查仓库、
实现备份、运行测试、接收真实故障与独立 oracle 的反馈，并继续修复。控制器
可以让 host 因注入故障而退出并冷恢复**同一个 TaskId**，但没有按 16/24 轮
重置的子任务、独立成功标签或新预算。每次候选进入实际负载前先在隔离副本
过安全/数据完整性门，冻结其源码摘要；切换版本要记录旧/新身份和同一数据库
的连续性。基线版本的负载时间不记为模型候选版本的通过时间。

目标是连续运行约 3 小时，其中**最终同一冻结候选版本**在同库并发负载中至少
持续 120 分钟。任务过早结束、候选从未进入负载、或只在最后运行一个短 smoke，
都如实记为“未达到长流程”，不靠睡眠或重复短测试凑时长。硬截止 6 小时；
截止时未达 120 分钟就是未通过，不延长原窗口。生产系统可按安全门提前停止，
停止后不以人工版继续跑出的时长替模型补分。

混合负载至少有四个独立安装 worker、一个读/GC worker、一个本地发布接收端和
持续备份/恢复校验器。规模固定并有确定 seed：多租户、多个环境、120 个包名与
多版本依赖、不断增长的收据历史；每批记录请求身份、期望 generation、真正
提交的收据、接收端发布身份和读到的指针。每 10 分钟检查进展/资源和完整性，
但这只是同一负载的观测点，不重启任务、不复位指标。结束后停止所有写者、
重开 SQLite，逐条复核整段历史与接收端账，并核对源输入的字节身份。

故障由控制器按固定 seed **穿插在持续负载中**，以可观察条件触发，而非作为
各自独立的模型小题：写入在指针发布前/后被真实杀死；备份暂存写完而发布前
死亡；接收端已提交但 ACK 丢失；catalog 更新导致旧证据失效；一次长纠正输入
在模型仍工作时送达；安全的模型/工具边界上断开 host 并从 checkpoint 冷恢复。
一次真实长工具取消必须在已结算供应商 attempt、已观察到操作被接受和进程仍
在运行时触发；取消 ACK、进程真正退出、已提交观察保全和恢复分别核对。
若触发条件没出现，记 `NOT_TRIGGERED`，不得由控制器伪造“已覆盖”。

## 独立判定与失败处理

oracle 不导入候选实现；从真实 SQLite、磁盘文件、ZIP、公开 host 事件与接收端
日志独立构造预期。在线快照成功必须对应调用开始与返回之间的一个可证明 cut：
每个 scope 的 generation 连续且 current 为最大值，历史收据/manifest/blob 全部
一致；未决 outbox 逐条保留；在途 journal 不得被静默省略。恢复后审计发布端，
同一身份至多一次外部提交，未知结果先查询。穿越路径、重复/多余 ZIP 成员、
损坏引用、跨租户混用、资源超限、旧指针和非匹配目标都要拒绝且源/目标字节不变。
oracle 至少用独立反例校准“坏 blob、丢收据、丢 outbox、ACK 已提交却重 POST、
恢复目标部分存在”；不能只靠候选自己测试的通过输出。

验收分开记：模型自主功能正确、同一版本 120 分钟负载、Runtime 的取消/冷恢复、
controller 自身完整性、用量与估算费用。任何一项失败不得被另一项代替。对每个
注入事件记录 `planned / fired / observed / verdict` 和原始效果身份。若模型生成
的代码有普通错误，给同一任务反馈并继续用剩余额度修；人工补修另建来源身份，
不纳入模型自主成绩。Core 权限绕过、跨任务状态认领、未知效果盲重放、证据或
预算账目不完整、进程清理未确认时，停止相应副作用分支并保留全部事实；
`RecoveryRequired` 不能通过删除 checkpoint 或重建工作区来消除。

## 提议硬界与实施准备

新 campaign 提议最多 **6 小时、260 次主模型决策、300 次供应商 attempts、
900 次工具尝试、800 万输入 token、22 万输出 token，估算 USD 2**。
每次模型请求最多 8192 输出 token；真实供应商只允许一个在飞 attempt，维护
模型调用上限 0。用完整 wire 字节和最坏输出先预约，Chat 用量严格解析，
未知/部分用量不补零且停止新受理。价格换算在启动前按当时官方表重新校验，
提额不能由控制器自行决定；账本估算不写成供应商账单。候选进程只访问隔离
工作区和本地接收端，不运行包 payload 或访问外网。控制器每次限时/限输出，
只终止自己创建的进程树。

拟沿用官方 `deepseek-flash` Chat 协议和**显式非思考模式**；官方文档目前默认
开启思考，带工具的多轮思考需要完整回传 `reasoning_content`，现有适配器不以
未实现的契约冒险。本方案使用的缓存命中仍是服务端观察，不是布局或费用因果
结论。协议与价格依据：[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)、
[Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)、
[Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/)（均须在启动当天复核）。

在正式运行前还需完成本方案的**可执行物**：冻结 `SPEC.md`、受保护基线与
独立 oracle；实现一个持续负载控制器及上述 fault gate；做零供应商的控制器
反例、实际 host route/schema 预检、预算/未知用量/启动清理测试。只有这些实际
检查通过，才能把方案标成 READY；当前是 `NOT_STARTED`。本计划没有授权
新一轮付费运行，也不改变已有未提交工作树。

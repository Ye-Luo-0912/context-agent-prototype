# KV 隔离预热与发送边界复测

2026-09-10，基线 `732cf93` 加工作树的布局/观测改动。本片用户结果：能够核实最终 HTTP 请求的稳定部分和服务端实际用量，避免用本地公共前缀冒充计费收益。复用已授权的本地 `eval.env`，不修改或记录凭据。

## 结论

**CurrentStateLast 的前缀稳定性确实到达了 HTTP 发送边界，但当前网关的状态变化请求仍没有报告缓存读取。单纯重排请求尚未解决这条环境的缓存成本问题。**

12 次请求，合成焦点/证据回答 12/12 正确。两种布局各经历冷请求、原样重放、两次状态变化及各自重放。所有 4 次状态变化调用都报告零读取；6 次原样重放中 5 次报告 9,728 / 10,609（91.70%）缓存读取，最后一次 Legacy 原样重放也出现零命中。

这批数据同时说明两个边界：客户端保留长前缀不足以保证状态变化后复用；即使完整 HTTP body 相同，也不保证每次都命中。两臂在重复组的差异不能证明布局有因果优势。没有确认路由、断点、隐藏消息重组或网关转发中的哪一种是根因。

## 本次控制条件

- 仍使用生产 PromptAssembler 和 OpenAiProvider，配置 Responses / `gpt-5.6-luna`，相同工具定义、模型配置、证据、查询序列；每次查询需要准确 key/serial/KEEP_FOCUS。
- 两臂在最初 policy 的前部使用各自稳定的新 nonce，降低首次实验的跨布局预热干扰。它分离的是提交的前缀，不代表能够控制服务端物理缓存池。
- 每臂顺序：round 0 冷请求 → round 0 原样重放 → round 1 改当前查询/进度 → round 1 重放 → round 2 改查询/进度 → round 2 重放。两臂发送次序交替 AB/BA；请求之间间隔 5 秒，给异步写入留出时间，但不把这当成已确认的写入时延上界。
- 共 12 次 provider 调用、显式协议、不接自动重试包装器；每次输出上限 512、超时 55 秒、响应字节上限 1 MiB。没有仓库工具执行，也没有发送私人仓库正文。
- 观测发生在 reqwest 已构建 HTTP request 上，随后发送同一 request。每次恰有 1 条请求观测，所有响应诊断均未截断。未添加 cache key、显式断点或其他供应商缓存参数。

## 对共同设计的修正

现有 `S（策略）→ E（合格证据）→ H（有界协议历史）→ D（完整当前状态）` 布局保留，Legacy 回退也保留。注意度、选中集合、语义有效性、正文角色、GC 和 Core 审批/提交未变；12 条合成查询正确不等于真实代码任务质量已验收。

接下来的最小功能应是**供应商无关的可复用边界 + 按能力启用的薄映射**，而不是继续冻结上下文来延长表面前缀：

1. 在最终 packing/必需正文覆盖完成后，从实际保留消息生成边界；例如标出最后一个稳定证据块的结尾。边界是派生的性能提示，不能带来权限、删除正文或 ACK 旧证据。索引失配/内容变更必须使提示失效。
2. 自动缓存的 provider 继续发送同一份完整请求。已确认支持显式断点的 provider，才把边界映射到其协议字段；正文角色和当前焦点仍逐字保留。能力由显式配置/验证决定，不从兼容接口或模型别名猜测。
3. 验收重点是“已经预热后，只改 D，仍能读取稳定 E 的缓存”，并检查当前任务回答。完整重放命中只作为缓存存在的对照，不再用来验收 Agent 迭代中的收益。
4. 如果该网关不接受/不保留边界，或相同请求仍因路由经常失配，则记录能力限制，再核实稳定路由或端点支持。客户端无法用布局保证隐藏服务行为，不为缓存把 Focus 降成 User，也不无限保留旧 System 状态。
5. 总费用而非命中率是目标。若普通/读取/写入单价是 p/r/w，且一个 S-token 前缀本来就要发送，新增写入溢价是 `(w-p)S`，k 次成功复用节省 `k(p-r)S`；只有后者更大才划算。路由命中概率、重建频率和额外保留 token 还会改变收支。当前网关价目/账单未核实，不代入官方单价计算金额。

[OpenAI 官方缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching)对 GPT-5.6 及后续模型区分了保存边界、查询边界与公共前缀，并给出显式断点；这支持边界抽象的必要性，但不能证明本次网关的未命中就是该机制导致。共同层保留供应商差异，不假设所有服务具有相同断点、TTL、写入费率或路由规则。

# 供应商 KV 布局首次实测

2026-09-10。用户授权复用本地已有供应商环境；仅从 git 忽略的 `eval.env` 读取配置，不修改该文件、不记录密钥。配置模型 `gpt-5.6-luna`，通过现有 Pinaic 网关使用 Responses；这只是配置模型名，未独立确认网关实际使用的上游模型或费率。

## 结论

**供应商缓存可用，但本次没有证明 CurrentStateLast 比 Legacy 更省输入费用。**10 次请求的焦点/证据回答均正确，原样重放对照均报告 9,728 / 10,602（91.76%）的缓存读取。状态变化时，新布局在客户端保持了约 20.7KB 公共前缀，服务端仍未报告缓存读取；旧布局则在第 8 次请求出现高命中。

这说明“本地公共前缀变长 ⇒ 本供应商立即高命中”这一推论不成立。数据包含预热、请求顺序和可能的跨布局缓存复用；不能据此判定两种布局的因果优劣，也不能声称节省了多少人民币或美元。首次测量不作为扩大布局改动、改变焦点角色或冻结上下文选择的依据。

## 方法和预算

- 使用生产 `PromptAssembler`、生产 `OpenAiProvider` 和本地配置的模型/协议；不使用 mock 响应。
- 128 条合成库存记录，4 个证据块。两种布局的每条消息内容、角色和工具定义相同，仅排列不同；离线夹具测试对此逐条检查。
- 每轮更换 CURRENT DIRECTIVE 的查询目标与 TaskProgress 版本，模型需返回目标、准确 serial 和 `KEEP_FOCUS`。没有把私人仓库正文、环境配置或密钥放入模型输入。
- 4 轮，发送顺序为 A/B、B/A、A/B、B/A；A=Legacy，B=CurrentStateLast。两臂使用同一个新 nonce 保持内容配对，因此不是完全隔离的缓存池。
- 最后分别重复一次第 4 轮的完整请求作为缓存正对照。总计 **10 次逻辑 provider 调用，无自动重试**，每次最多 512 个输出 Token，单次超时 55 秒。
- 为限制费用，子进程将原配置的输出上限 4096 降到 512，其他已配置模型/协议/采样参数保留。未发送新缓存 key、显式断点或供应商专属控制参数。
- 记录的是合成焦点/证据查询表现，不是代码修改、长期 Agent 工作流或整仓任务成功率。

## 数值结果

每次输入都是 10,602 tokens；10 次总输入 **106,020**，缓存读取 **29,184**，输出 **367**。每次 cached_input_tokens 均有报告，本批该字段覆盖率 100%。

| 阶段 | 布局 | 次数 | 输入 tokens | 缓存读取 tokens | 缓存读取比例 | 平均总耗时 |
|---|---|---:|---:|---:|---:|---:|
| 首次＋状态变化 | Legacy | 4 | 42,408 | 9,728 | 22.94% | 3,711.5 ms |
| 首次＋状态变化 | CurrentStateLast | 4 | 42,408 | 0 | 0% | 2,817.25 ms |
| 完整请求原样重放 | Legacy | 1 | 10,602 | 9,728 | 91.76% | 3,094 ms |
| 完整请求原样重放 | CurrentStateLast | 1 | 10,602 | 9,728 | 91.76% | 3,873 ms |

均值只是描述这几个调用，样本不足以做延迟显著性判断。输出长度和服务端负载等条件也会影响耗时，不把较短耗时归因于 KV 改善。

| 请求序号 | 布局 | 状态轮次 | 本地相邻同布局消息 LCP 字节 | 服务端缓存读取 tokens |
|---|---|---:|---:|---:|
| 1 | Legacy | 0 | — | 0 |
| 2 | CurrentStateLast | 0 | — | 0 |
| 3 | CurrentStateLast | 1 | 20,688 | 0 |
| 4 | Legacy | 1 | 547 | 0 |
| 5 | Legacy | 2 | 547 | 0 |
| 6 | CurrentStateLast | 2 | 20,688 | 0 |
| 7 | CurrentStateLast | 3 | 20,688 | 0 |
| 8 | Legacy | 3 | 547 | 9,728 |
| 9 | Legacy | 3，原样重复 | 20,961 | 9,728 |
| 10 | CurrentStateLast | 3，原样重复 | 20,961 | 9,728 |

LCP 比較的是逐条 ModelMessage 的 JSON 编码，不是供应商的隐藏渲染、tokenization 或服务端缓存键。尤其第 8 次请求前已有同一状态的另一布局请求，不能只拿它与上一次 Legacy 的 LCP 推断服务端违反前缀规则。

## 费用能说到哪里

本次有真实 input/output/cache-read token 数据。当前适配器没有采集独立的 cache-write token；网关收费表、实际账单与上游模型没有核对，因此金额仍为 **UNKNOWN**。

若 W 为本批写入缓存的输入 tokens，p/r/w/o 分别为普通输入、缓存读取、缓存写入和输出的单位价格，则分类不重叠时：

`C = (76,836 − W) p + 29,184 r + W w + 367 o`

若服务商不区分写入价格，则按其实际计费规则合并项。不能把 91.76% 的缓存读取比例直接说成 91.76% 的费用降低，更不能用官方网关之外的标价替代当前网关账单。

## 工程判断与下一步

共同底层仍保持当前约束：Context 决定合格证据，Runtime/Core 决定事实与权限，布局层不冻结焦点/正文，也不为命中而降级 Focus 的角色。

这批数据把下一步优先级改为**补齐发送边界与服务侧可观测性，然后做能区分原因的对照**，而不是继续依据客户端 LCP 调整布局：

1. 在最终 wire 构建点记录有界的工具/配置/消息段指纹和布局版本；继续避免记录密钥或完整正文。区分“组装层相同”与“最终发送层相同”。
2. 用类型化可选字段记录服务端实际模型标识、读/写缓存用量及缺失状态。无法观察服务端内部前缀就标 unknown，不能反向猜测。
3. 后续另行安排有预算的隔离测试：先预热，再分别只改进度、只追加工具交换、只改正文版本；换序重复，避免本次同一状态跨布局紧邻请求的干扰。完整请求重放继续作为对照。
4. 消息规范化、预热和路由都是**待验证假设**；本次没有确认其中任何一个是原因。不默认给所有供应商加同一个 cache 参数，也不把此网关的表现泛化给 OpenAI/DeepSeek 的全部服务。
5. 只有实际缓存/费用数据支持且任务结果不退步，再扩大布局优化范围。现有 Legacy 入口保留；本轮不再改变生产焦点/上下文或追加更多付费请求。

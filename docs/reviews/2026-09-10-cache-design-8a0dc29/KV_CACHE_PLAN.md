# 供应商 KV / 前缀缓存优化方案

**实测修正（2026-09-10）：**发送边界观测与 [12 次隔离预热复测](../2026-09-10-cache-live/ISOLATED_REPORT.md)已完成：新布局保留超过 20KB 的实际 HTTP 前缀，改变焦点/进度后仍报告零缓存读取；原样重放 5/6 命中。下一切片优先补**最终 packing 后的共同复用边界＋按能力映射**，区分“字节相同”“服务方已经保存”“本次可查找”和“路由可达”。继续保留全部焦点/上下文语义；仅布局稳定性不能作为费用收益验收。模型和计费分类均以服务方自报为观测，不能反推隐藏上游身份或金额。

**实施更新（2026-09-10）：**共同布局第一切片已完成，见 [KV_LAYOUT_IMPLEMENTATION.md](KV_LAYOUT_IMPLEMENTATION.md)：完整目录与 Focus/TaskAnchor/TaskProgress 后置，保留当前上下文策略，提供 Legacy 回退。本文其余内容仍为路线；区段化、正文元数据拆分、供应商参数与实际成本验收尚未实施。

用户已明确：目标是降低供应商输入 Token 费用。本计划只讨论供应商缓存；本地正文缓存、工具 memo、向量检索均不作为本轮缓存优化任务。方案基于 `8a0dc29` 的请求链路复核，W02 修复已包含在随后到达的 `6ec044a`。这是设计，尚未改变生产请求布局。

## 共同底层：语义投影与请求布局各自演进

已有 ContextEngine 继续回答“当前哪些内容有资格进入请求”；Runtime/Core 继续提供任务、执行和权限事实。PromptAssembler 负责回答“这些内容怎样排列，才能让供应商复用更多已有前缀”。两个阶段不能共用一个每轮变化的渲染版本。

```text
Runtime/Core 当前事实       ContextEngine 合格证据
             \               /
              PromptAssembler
       验证输入 → 稳定布局 → 最终覆盖与预算
                      |
     messages + tools + 可选的前缀复用边界
                      |
              现有 ModelTransport
          /            |             \
      OpenAI        DeepSeek        其他兼容接口
```

复用边界是优化建议，不能替代消息正文。任何适配器忽略建议时，都必须能够发送完整有效请求。原始历史、任务状态、审批、验证 receipt 与恢复权仍只有现有权威。

### 最小结构，留在现有模块

以下为目标职责的伪结构；实际首切片使用 `PromptLayout` 枚举与 `ModelInput.current_state_frame`，没有新增下面这些状态容器：

```rust
PromptLayout {
    stable_policy,      // 稳定的高权限策略
    evidence_segments, // 有来源/版本/范围的低权限内容
    protocol_tail,     // 完整且有序的工具交换
    current_view,      // 当前完整指令与类型化状态的投影
    tools,             // 本轮实际合法的工具定义
    reuse_boundaries,  // 上述稳定部分的边界，不传入正文
}

PromptLayoutState {
    base_signature,
    ordered_segment_keys,
    protocol_start,
    retained_bytes,
}
```

- `PromptLayoutState` 放在 ActiveTurn，记录有界顺序和投影身份，不保存第二套任务/事实，不重复存整份 prompt。恢复时允许直接丢弃重建。
- 段 key 包含来源/归属、内容版本或 digest、范围、表示版本；热度、驻留计数、当前时间和 materialization_id 不进入内容 key。段 key 是应用的表示身份，不能让供应商随机复用中间块。
- 最终 provider 指纹另包含角色、工具定义和真正影响模型渲染的配置；本地 key 相同不自动等于服务端命中。
- 现有 ModelRequest 仍完整承载 messages/tools；可选 hints 只携带边界/稳定归组信息。共享契约仍由单一维护者调整，不导出 RuntimeCommand 或 CorePort。

### 每轮执行算法

1. Runtime/Context 正常产生新的当前事实、候选、必需正文和有效性结论，不跳过 materialize/审批/验证。
2. 对合格内容形成稳定段身份；同一个选中集合保持已有顺序，纯渲染不带冷热/访问计数。不能为了命中冻结过期的语义状态或取消必需证据。
3. 在策略、证据基座及工具定义仍一致时，复用其表示，按原顺序追加新完成的工具交换；只重建当前状态 D。
4. 真正的正文/资格/指令/工具定义变化或预算不足时，从最早受影响的位置重建。后续字节即使未变，也承认供应商前缀可能失效，不能声称按块局部命中 KV。
5. 对最终完整请求重新做预算和正文覆盖检查。只有实际发送且成功消费的内容进入本次 ACK，绝不复用旧消费身份。
6. 发送后记录实际 provider 用量与布局变化原因；缺少 usage 的接口标 unknown，不从本地指纹推断真实命中。

### 两种更新频率

| 改变 | 当前语义状态 | 稳定段 |
|---|---|---|
| 进度、待办、验证结果、当前 Fresh/Unknown | 每轮重新投影 D | 内容仍合格且字节不变时保持 |
| 冷热迁移、注意度变化、诊断计数 | Context 照常处理；必要信息进 D/遥测 | 单凭这些变化不改写正文表示；若导致合格集合变化则正常重建 |
| 新工具结果 | 新状态与结果立即可见 | H 追加完整交换 |
| 用户约束、语义资格、文件版本、工具权限/定义变更 | 立即生效 | 必要部分重建，接受 miss |
| 窗口达到上限 | 仍满足必需证据与输出预留 | 一次重建有界尾部，进入下一个区段 |
| 恢复或切换任务 | 按现有验证流程建立当前状态 | 丢弃派生布局，冷启动不影响正确性 |

共同方案的验收是“相同的有效信息保持相同的前部表示；新的状态及时出现；任何缓存失效都不改变执行正确性”。首轮无需依赖显式断点、某个路由 key 或特定 TTL。

## 首要改动：让前缀长时间保持一致

现有请求：

```text
tools（动态集合）
system policy / runtime facts / 未加载工具目录
TaskAnchor + TaskProgress + Focus（每轮变化）
工作集统计 + 带注意度/当前性标记的正文
滚动 checkpoint note + 最近 6 组工具交换
```

进度、目录、统计在前部变化，会截断后续大正文的公共前缀。供应商还可能把工具定义放入模型渲染的前部，所以只调整 messages 不足以处理 schemas 变化。

建议逐步形成：

```text
稳定的有界 tools 定义 / 模型与格式配置
S：固定策略、不变宿主信息
E：本区段稳定的证据正文/摘要（身份、版本、范围固定）
H：本区段执行历史（完整工具交换，保序追加）
D：本次完整指令、当前进度、版本有效性、缺失和可调用状态
```

依然由 Context 决定哪些证据有效、由 Core 决定操作权限与提交；PromptAssembler 负责把有资格的内容放在可复用的位置。缓存命中不减少 Context Window 占用，不减免这些检查。

## 三个优先级

### 1. 稳定 schemas 和最前面的消息

- 固定同一有界工具集合的名称、顺序、描述和 schema 序列化；先核对同阶段是否真的需要频繁切换集合，不永久展示全部工具。
- 未加载工具目录不再作为早期 system 的动态补集，当前可用性放入 D。工具本身的内容与权限仍分开；Core captured surface 不冻结、不绕过撤销。
- 支持的 provider 可以稳定工具定义并另限制 callable subset，或追加新工具定义；不支持时保留原安全行为，在真正换工具集合时接受前缀重建。
- workspace marker、catalog 计数、attention、Fresh/Unknown 等变化从大正文前部移到 D 或已有遥测。语义过期立即失效，不因缓存收益保留旧约束。
- `prompt_cache_key` 若受支持，按稳定的 workspace/task/layout 归组；不加入 request_id、turn_id、每轮 revision 或当前时间。它不能覆盖前缀不一致。

### 2. 状态后置，历史在有界区段内追加

初版先使用 `S || E || H || D`；只改 D 时保持前面不变。新的工具交换添加在 H 尾部，旧 D 不成为新的持久任务状态。支持显式断点时，标记 E/H 的稳定末尾，避免专门写入很快变化的 D。

自动缓存接口不一定在任意 LCP 处已有缓存单元，应在多轮实测中观察预热和断点命中。如果该供应商对完整先前请求的追加复用明显更有效，可以在同一有界区段内保留旧状态快照并追加新快照，但必须明确其历史性质；最新完整状态继续由 Runtime 派生，强语义变更重建区段。这是能力相关的后续选择，不能默认无限累积旧 system 状态。

读取、修改、验证顺序不改变；同一历史 tool call 的 id、arguments、结果逐字保持稳定。新用户指令、权限/工具定义撤销、所选正文资格或版本改变时重新组装，允许必要 miss。

### 3. 避免每轮滑动重写大段前缀

当前超过 6 组后每轮移动窗口、改写 checkpoint note，持续切断历史前缀。建议在现有硬上限内采用区段：到阈值一次重建短尾与稳定摘要，之后追加至下一阈值。不要提高历史上限来制造表面高命中率。

Context 的冷热迁移不要求立刻改写仍有效的正文表示；选中集合、证据有效性或 required coverage 真正变化则重建。区段只管理请求表示，不成为第二个 ContextEngine，不改变原始历史和 Storage GC。

## 数学上看净费用

令输入总量 N、缓存读取 H、缓存写入 W，普通/读取/写入单价分别为 p、r、w。在供应商把这三类 token 分开计费时：

`C_input = (N − H − W) × p + H × r + W × w`

没有独立写入费用的供应商采用其对应公式；未知字段不能当成零。目标是降低整个任务的总费用，并同时限制轮数、输出、维护调用和长历史膨胀。

**仅作算术示例，不是本仓库实测或价格承诺：**每次输入 30,000 tokens，其中稳定前缀 24,000，变化尾部 6,000；假设缓存读价 0.1p，写价 1.25p，稳定前缀首次写入、随后完整命中，尾部不写缓存。

- 首次：`24,000×1.25p + 6,000p = 36,000p`。
- 后续一次：`24,000×0.1p + 6,000p = 8,400p`。
- 共 10 次：`36,000p + 9×8,400p = 111,600p`，相对全不命中的 `300,000p` 少 62.8%。

断点不可用、缓存未就绪/过期、路由和重建都会降低收益。因此不要承诺这个降幅，也不要为了跨过最低缓存门槛填充无用文本。

本地实际结构探针中，增加一条进度使公共前缀从 5,576 字节降到 309；后置状态的布局对照为 5,573。它证明排列具有改善空间，**不等于 token 命中率**。数据见 [prefix-locality.json](evidence/prefix-locality.json)。

## Provider 差异必须在适配器中处理

OpenAI 的前缀匹配、路由 key、显式断点与写入计费支持取决于模型；仅给 endpoint 加 key 不能修复变化的前缀。[官方文档](https://developers.openai.com/api/docs/guides/prompt-caching)

DeepSeek 当前文档说明缓存自动启用、以已经持久化的前缀单元匹配；公共前缀检测可能在后续请求才形成可命中的单元。其 usage 使用 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。[官方文档](https://api-docs.deepseek.com/guides/kv_cache/)

**本仓库观测还有一个缺口：**`provider-openai/src/sse.rs::WireUsage` 目前只读取 OpenAI 的 `prompt_tokens_details.cached_tokens`，不读取 DeepSeek 上述字段。若使用这种返回格式，当前 Runtime 会得到 unknown，而非真实零命中。先正确区分“确实低命中”和“供应商已命中但没有记到账”；缺少统计字段本身不会改变供应商实际账单。当前供应商/模型尚未由用户确认，不能根据 README 示例推断实际使用的是 DeepSeek。

## 实施顺序与验收

1. **共同布局首切片：**在 PromptAssembler 显式区分稳定段与 current_view，稳定同一合法工具集合的序列化，迁移高频状态到末尾；保持 Context 策略、Core 权限、硬预算和原有协议配对。同步记录段指纹和变化原因，先不接供应商专属参数。
2. **共同区段切片：**让执行历史在原上限内追加，到边界才重建；同步处理必需正文回注、最终覆盖和新的 consumption ACK。任何无法合法复用的输入退回完整重建，不能退回过期信息。
3. **薄适配层：**按运行环境能力可选映射缓存 key、断点等，并归一化 read/miss/write/unknown；不用给所有兼容服务强行发送同一字段。usage 兼容修复可作为独立小切片，不是共同布局的架构前置。
4. **真实成本验收：**同一任务、同一模型与工具需求，对照预热、追加、修改、重建、恢复场景；比较总输入费用、输出/维护费用、决策轮数、完成正确性。不能只比较 hit ratio。

首切片的必要测试包括：相同有效证据＋不同进度/驻留统计保持稳定前部；纯追加不改旧交换；新指令/版本/权限即时生效；最终必需正文、预算和 ACK 正确；不识别 hints 的 provider 仍可发送完整有效请求。不新建数据库或调度器。

真实 provider 调用及成本对照目前 **NOT_RUN**。供应商选择由运行环境决定，共同底层的设计和实施不等待该选择；不同服务的实际收益在后续验收中如实测量。

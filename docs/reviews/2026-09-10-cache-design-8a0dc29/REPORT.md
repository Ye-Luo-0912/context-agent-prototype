## 结论

现有架构可以保留。缓存不友好的主要原因是：**每轮重新投影的状态先出现，稳定的大块正文与协议历史后出现**。上下文选择、冷热迁移、工具加载、滚动截断又会改变前部表示。为正文增加哈希或为请求增加 `prompt_cache_key`，都不能单独修复这个排列问题。

建议保留 Context 的选择与生命周期职责，单独改进 PromptAssembler 的布局：**稳定头部 → 有界证据基座 → 已完成的工具交换 → 当前决策状态**。高频状态只重建末尾；协议历史按有界区段重建；正文缓存以内容版本和范围为键。所有缓存都是可丢弃的派生结果，不决定权限、完成、验证或恢复。

W 系列的主体确实已落地，但“全部收口”需要以下限定。W02 复核缺陷本次已修；W04 和 W06 仍有可执行反例。先关闭这些小边界，再实施缓存观测与布局，不需要再起一轮全仓清零。

## 2. 缓存到底缓存什么

| 层 | 已有基础 | 可以省什么 | 不能据此推出什么 |
|---|---|---|---|
| Provider 前缀/KV | 两种 OpenAI wire 路径；已接 `cached_input_tokens: Option<u64>` | 重复前缀的计算与部分输入费用 | 命中不等于新验证；不保证减少输出、模型轮数或总耗时 |
| 当轮正文 | `ProtocolBodyCache`：4 条×8KiB，path/digest，未知修改后休眠 | 把仍可信但被协议窗口挤掉的正文回注，可能少一次重读轮次 | path@digest 不等于任意行区间都可见 |
| 只读工具 memo | `execution/memo.rs` 目前始终 miss，未接 dispatch | 在模型已经决定读之后节省 I/O | 通常省不了那个模型决策轮；不能缓存写操作或可信验证结论 |
| Context 派生计算 | 现有目录/实体/依赖索引、plan/read/commit 及 materialization ACK | 搜索候选、不可变正文读取和纯渲染的重复工作 | `materialize()` 不是无副作用纯函数，不能直接把旧输出和旧 ACK 整包返回 |

这四层不要合并成一个“语义缓存”。尤其不要用相似查询命中去替代工具执行或复用 LLM 的行动答案。

## 4. 数学上优化的目标

令每轮的真实模型渲染为 `P_t`，相邻轮共享前缀为 `L_t=LCP(P_t,P_(t+1))`。相同正文散落在不同位置，不构成前缀复用。真实可复用量还取决于服务端已有的历史前缀、断点、模型配置、路由及存活时间，不能简单把 `L_t` 当成命中 token。

把提示拆成有序块 `B_i`；若块保持相同的概率为 `p_i`，在各块变化独立、仅计完整块的简化下：

`E[shared_prefix] = Σ_i |B_i| × Π_(j≤i) p_j`

这解释了为什么早期一个高频变化的小字段，会损失后面低频变化的大正文。重排必须先满足角色权限、工具调用配对、当前指令完整性和证据有效性，不能按这条公式任意交换消息。

实际目标应是：

`min J = 输入/缓存写入/输出费用 + λ × 任务总延迟 + μ × 峰值内存`

约束：必需证据可见、当前指令完整、Core 审批和提交不变、资源有界、旧结果不冒充新验证。任务总延迟包括维护模型调用、工具往返和多余决策轮。因此“命中率高”不一定比少一次无用读取更好。

对于一个重建后可以稳定使用 K 轮的区段，设重建代价 A、每轮增加 a tokens、额外历史的单位边际代价 ρ。忽略波动后的摊销近似：

`f(K) = A/K + ρa(K−1)/2`，内点最优 `K ≈ sqrt(2A/(ρa))`。

这不是现在要调的算法参数。它说明无限追加和每轮滑动都不是普遍最优；必须在既有窗口、输出预留和正文预算内折中，遇到指令或证据失效立即重建。真实 A/ρ 需要 provider 实测，不能由本次字节探针估出。

## 5. 建议的具体布局

```text
S：稳定策略 + 不变的宿主事实 + 有界工具定义版本
E：本区段的证据正文/摘要（保留原低权限角色、身份、版本、范围）
H：本区段已完成的工具交换（成组、保序、在区段内只追加）
D：当前完整指令、任务约束/进度、Fresh/Unknown、当前可调用工具、必需缺失
```

新一轮形成 `S || E || H_old || new_exchange || D_new`。旧 D 不进入 H，不积累过期的“当前状态”。新的模型请求仍包含完整 D；缓存的是它之前的稳定表示。S 中明确状态由最新 D 投影给出，但可信完成仍由类型化 Runtime/Core 判定，不能靠提示语保证正确性。

### 稳定表示与当前状态分开

- 内容块保存不可变身份与确切范围；不要把热度、驻留位置、每轮计数混进正文标题。对模型决策有用的变化放 D；纯遥测放现有事件。有效性变化不能因布局稳定而延后。
- 选哪些证据继续由现有 Context 策略决定；只稳定同一选中集合的表示与可合法稳定的排列。范围/集合真的变了就重建相应段，不能为了命中保留不合格候选。
- 不把文件正文升格为 system。迁移当前状态位置保留权限等级；工具调用与结果必须成组。兼容 endpoint 若不支持这种消息位置，使用原布局；请求有效不代表 LLM 行为相同，需另做真实任务验收。
- 每次都按**最终实际请求**重算覆盖与预算，并生成新的 materialization/consumption 身份。旧渲染内容可复用，旧 pending ACK、lease、审批、receipt 决策不能复用。

### 有界区段，不无限追加

先稳定 S 和 D，再考虑 H 的区段化。沿用现有最大 6 组及 token/字节上限；到边界时一次重建较短的尾部，留下有限追加空间，而不是无限保存历史。具体低水位需小范围验收，因为更早移出工具正文可能增加重读。

checkpoint 的 receipt 摘要在一个区段内固定，新结果留在 H 或 D；下一次区段重建才重新形成摘要。不得改写已完成组的 tool_call_id、arguments 或结果。必需正文仍由 Context/正文回注补齐，验证证明继续由 ExecutionState 管理。

以下事件应触发重新授权或重建：新用户约束、任务/指令身份切换、已选正文版本或语义资格改变、工具定义/权限撤销、窗口超限、恢复。纯热度/驻留改变不自动使内容字节失效；能否继续作为当前证据由现有语义/归属/完整性检查决定。

### 工具 schema 稳定需要独立处理

把“工具定义版本”与“本轮是否允许调用”区分，但 Core 的 captured surface 始终是执行依据。先保持既有有界工具集合、确定性顺序和描述，不把全仓工具永久塞进前缀。

Provider 支持时，可使用稳定的有界定义集合配合可调用限制，或使用其追加工具定义机制。撤销权限仍要即时生效；仅在 D 写“不可调用”不构成执行隔离。不支持的兼容接口照旧发送当前 surface，接受必要的缓存失效。

### 缓存只是 ActiveTurn/适配器的派生状态

区段号、序列化版本、工具定义指纹、已有段的摘要和大小，可放在 ActiveTurn 的有界布局状态中；不新增持久任务模型。正文最多沿用现有缓存额度，先不增加副本或保存整份历史请求。恢复/进程重启允许冷启动重建；KV 缓存不参与恢复正确性，不能写入 checkpoint 充当授权。

## 6. 各层缓存键与失效条件

| 对象 | 最少需要的身份/依赖 | 命中后仍要检查 |
|---|---|---|
| 不可变正文及其渲染 | workspace/来源，content digest，完整范围，编码/表示版本；item 身份保留来源关系 | 当前语义、task/scope 归属、真实范围、请求预算；字节存在不表示 Fresh |
| fs.read memo（以后） | 上述身份＋规范化参数、读取语义版本 | Core 仍处理请求权限；新 call_id 和来源账目；需可信的当前内容版本，mtime 不足；旧读不能成为新验证 |
| Context 搜索候选 | 引擎/目录实例版本、query、task/scope、筛选条件、排序、cursor、limit、读取预算 | 重新检查候选资格和完整性；PARTIAL、已读预算、游标一起缓存，空的 PARTIAL 不是不存在 |
| 纯候选评分/正文编码 | 所有实际依赖的内容/语义/焦点/策略版本 | 只缓存纯阶段；`materialize()` 自身仍执行新 preview 和 ACK 流程 |
| Provider prefix | 最终模型渲染及对应模型、工具/格式等配置 | server hit/TTL/路由，不能本地宣布命中；cache key 只辅助归组 |

未知工作区修改：保留不可变字节，挂起“当前事实”资格；VersionOracle 证明相同版本后才恢复可用。具体路径已修改只失效相关当前绑定。恢复产生新实例代际，避免旧缓存键或 ACK 的 ABA；单一 gc_epoch 不足以代表所有可影响搜索结果的变化。

不缓存写工具、shell 副作用、审批结论、任务完成权或“测试通过”决定。`fs.read` memo 第一版也必须先有已知当前版本；没有版本证明就正常读取，不能为省读而省掉版本确认。检索继续利用现有索引，没有必要为这项设计引入向量库。

## 7. Provider 适配与观测

2026-09-10 核对了 [OpenAI Prompt caching 官方文档](https://developers.openai.com/api/docs/guides/prompt-caching)。它要求渲染前缀匹配，工具和部分请求配置也影响前缀；`prompt_cache_key` 是路由提示，不是内容相同的证明。新旧模型的断点、写入计费与保留选项不同；支持的模型可显式标记稳定段边界，变化尾部不必写缓存。具体支持能力应由 provider/model 配置声明，不能对所有 OpenAI-compatible endpoint 默认发送同一参数。

仓库已读取 cached_input_tokens，但尚未表达缓存写入 token。若 provider 区分写入费用，只统计 read hit 不足以计算净收益。新增字段需 optional/serde default，未上报保持 unknown。不要把 `store:false` 误解成已禁用前缀缓存，也不要把服务端会话保留当成 Runtime Checkpoint。

下一切片先让开发者能回答“本轮为何失去复用机会”：在现有事件中增加有界的布局版本、段长度/摘要、schema/config 变化原因、观测覆盖范围。相邻请求仅保留受预算约束的指纹/摘要；只能证明整消息/整块前缀时，报告该粒度，不能编造精确 token LCP。哈希隐藏正文但并非匿名化保证，不额外记录原始请求。

指标至少同时看：

- `Σ cached_input_tokens / Σ input_tokens`（只对确实报告这些字段的调用统计，并注明覆盖率），cache writes/unknown；
- 总 input/output/维护 token、provider 重试未知费用、首响应时间与任务总耗时；
- 决策轮数、重复读取次数与已有 FsReadMotive、required_miss、验证/完成结果；
- 区段重建原因/次数、缓存字节与条目峰值、恢复后的冷启动情况。

只有正确性指标不退步且净成本/延迟改善，才推广布局或扩大缓存。实际收益的取舍是减少重算与避免过长历史共同决定的，不能单看缓存命中百分比。

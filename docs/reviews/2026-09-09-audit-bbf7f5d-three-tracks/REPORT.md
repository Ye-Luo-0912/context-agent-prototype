## 三、上下文、GC、搜索：这次最重要的问题

### 1. 默认 Rolling 策略在第二次折叠时，没有把上一次摘要作为输入

**位置：** `crates/context-baselines/src/rolling.rs` `take_fold_job` / `compact_fold` / `maintain`

当前折叠任务的 `prior` 从空字符串开始，只加入这次从 `records` 移出的内容。旧摘要参与的是身份处理，**旧摘要正文没有进入下一次压缩输入**；压缩完成后又覆盖 `state.summary`。

因此会出现：

```text
第一轮：
A 约束 → 摘要 A

第二轮：
B 阶段内容 → 摘要 B
               ↑
       压缩输入没有摘要 A

保留状态最后只剩摘要 B
```

这不是模型"总结得不好"，而是它根本没有得到需要继续保留的旧摘要。

**它也不能仅作为离线基线问题后置，因为正式宿主当前仍默认选择 Rolling。**

最小修复应当是：明确把**旧摘要＋本次新增折叠内容**组成下一次输入，并记录来源覆盖；折叠失败、取消时保留原状态。先用确定性 compactor 检查实际输入，确认第二、三次折叠仍能访问第一轮的独有约束，再讨论摘要质量。

另外，当前任务文档已经承认：**Rolling 不跟踪 focus，活动任务检查点恢复会 fail-closed。**这是已有未完成项，不是这轮新发现；但它必须与默认产品配置一起解决。信封解码修好了，不代表默认 profile 的冷恢复已经闭环。

### 2. Context 截断正文后，仍可能声称覆盖完整行范围

**位置：** `context-simple/src/item.rs`、`context-simple/src/gc/reachability.rs`、`context-simple/src/materializer.rs`

`make_item` 会把正文裁剪到 `max_item_chars`，并追加截断标记；但文件读取的原始行范围仍可能保留。相同 revision 的覆盖判断，先比较行范围是否包含，之后才检查部分截断情形。

例如：

```text
旧片段：第 280–290 行，完整
新读取：第 1–300 行，文本较长
Context 入库：只保留前 16,000 字符，实际已没有第 280 行

元数据仍写：第 1–300 行
覆盖判断：新片段包含旧片段
结果：旧片段可能被 supersede
```

300 行处于当前 `fs.read` 的合法窗口范围内，因此不需要构造超出工具范围的请求。

物化侧还有同一类问题：有些 `partial_body` 判断只反映**本次装配有没有继续裁剪**，没有充分传播**源正文早已被 Context 裁剪**的事实；required 路径也存在直接标为非 partial 的情况。

建议明确区分：

| 字段含义 | 不能被什么替代 |
| --- | --- |
| 整个资源的 revision | 不能证明读取了全文 |
| 工具实际返回的区间 | 不能证明 Context 保留了整个区间 |
| 当前保留的正文与区间 | 不能被原始行范围覆盖 |
| 原文／摘要／描述符／partial | 不能只靠"本轮没有再裁剪"判断 |

**先修覆盖证明和 partial 传播，不需要新建一个巨大的 Frame 系统。**是否进一步影响最终完成门禁，需要端到端回归，本轮没有把它写成已证实的权限绕过。

### 3. GC recall 后删除 blob，发生在新的持久状态成立之前

这是本轮优先级很高的可靠性问题。

当前完整 GC 的过程是：

```text
读取 Stored blob
  → 把条目重新放入内存
  → 从 external map 移除
  → 返回 recalled_ids
  → 删除对应磁盘 blob
```

`commit_full_gc` 注释中的"commit"，实际上是**内存状态提交**。`engine.gc()` 随后执行 blob 删除，中间没有新的完整持久检查点屏障。

Runtime 的回合提交路径还显示：GC 发生在该回合的 durable commit barrier 之前。

风险路径是：

```text
检查点 C 记录：item 在 Stored，正文位于 blob X
  → GC recall，把正文装回 RAM
  → 删除 X
  → 新持久状态还没建立，进程中断
  → 恢复 C，仍然需要 X
  → X 已不存在
```

**内存里重新有了一份，不代表磁盘上的旧恢复根可以失效。**

建议把"驻留迁移"和"物理删除"分开。保留可恢复正文；只有能证明它不再被当前或仍受支持的检查点引用时，才交给 Storage GC 删除。可以复用现有 checkpoint 保留窗口和 store，不需要新数据库。

本轮没有运行 Rust 崩溃恢复测试。其他日志或工件可能有副本，但**不能把可能存在的人工补救当成这条恢复链的已实现保证**。

### 4. GC 外置的普通错误有回退，但取消不一定进入回退

当前 GC 计划会把 `pending_externalize_retry` 取走，也会把 Warm 溢出的条目移入局部计划；随后等待异步写入。写入返回错误时，提交阶段能把条目放回重试列表。

但如果整个 future 在等待期间被丢弃：

**正常错误分支和后面的提交阶段都不会执行。**条目若只由局部计划持有，未写出的内容就没有被归还到运行状态。

Tokio 的取消会销毁任务在暂停点持有的局部变量；`JoinSet` 被丢弃也会中止其中任务。这些机制不会自动回滚应用已经做出的容器迁移。（docs.rs tokio::task）

这里需要控制结论范围：**这是公开 ContextEngine future 的取消安全缺口，不是已经证明用户点击 `/cancel` 必然中断这个 GC 调用。**当前 Actor 在某些回合边界会直接等待 GC，普通取消的实际可达路径需要单独验证。

最小修复是让源条目在提交前始终保持可追踪的 owner，或者使用窄范围的 pending 事务／守卫。不要把"没有持锁跨 I/O"误认为"已经具备取消安全"。

### 5. 隔离失败后移除 owner，可能让下一次对账重新接纳坏文件

**位置：** `context-simple/src/store.rs` `run_reconcile_io` / `quarantine` / `commit_reconcile`

当前 checksum 不匹配时会尝试隔离文件，但隔离操作失败后，相关 ID 仍会进入 owner 移除集合。

于是可能形成：

```text
第一次扫描：
已有 owner + checksum 不符
  → quarantine rename 失败
  → 原路径文件还在
  → 原 owner 被移除

第二次扫描：
有效 JSON + 相同 item_id + 没有 owner
  → 当成可重建的无主文件
  → 用改动后的内容建立新 checksum 基线
```

**一次完整性拒绝，不能因为隔离失败而变成下次更容易接受。**

建议让隔离返回明确结果；失败时保留原 owner 或明确的拒绝／隔离状态。成功迁移、缺失、损坏、I/O 失败分别处理，不能统统归为"owner 已经可以删除"。

本轮在临时目录实际验证了隔离目标不可用、原文件仍保留的文件操作机制；两次 owner 转换是控制流模型，不是仓库回归测试。

### 6. 显式 admit 还有两个小而真实的语义问题

| 情况 | 当前行为 | 建议 |
| --- | --- | --- |
| 准入一个终态 Warm 条目 | 先从 buffer `remove`，再检查 semantic 并拒绝 | 验证必须在迁移前；拒绝路径不改变记录、索引和归属 |
| 准入一个较老、仍 Live 的 Stored Ephemeral 条目 | 保留旧创建时间，但没有新的有限使用期；下一次维护可能立即 TTL 终结 | 保留创建时钟，同时明确准入租约／有限使用期；不支持时一开始就拒绝 |

代码分别位于 `directive.rs` 和 `residency.rs`。

第二项尤其需要避免用错误方法修复：**不要为了让条目看起来"新"，篡改原始创建时间。**创建身份、最近访问、当前准入和到期保护，本来就是不同的时钟。

## 四、平台与客户端：事件接通之后，还需要修正一致性

### 1. 快照与订阅之间仍会漏掉一段变化

客户端目前先取得快照，再发起订阅；没有把快照游标带入订阅，也没有使用订阅返回的 watermark／resync 结果。服务端订阅则建立自己的较晚切点，并过滤不高于该切点的事件。

例如：

```text
客户端快照：seq = 100
期间发生变化：101、102、103
服务端订阅切点：103

服务端只发送 >103
客户端却仍使用 seq=100 的快照
```

101–103 既没有体现在旧快照里，也不会进入后续流。

应当提供**同一切点的快照与订阅**，或者先注册并缓冲事件，再取快照，以这个快照的切点去重。无需承诺无限重放，也无需新建 Chronicle 数据库。

还有相邻问题：**live-only delta 会重复前一个 durable seq，不能用 durable watermark 一刀切过滤。**跨重连时，停止旧 producer 也不会自动清掉队列里已经存在的旧代事件，需要有序的 epoch／reset／snapshot 边界。

### 2. 新队列的 `Completion` 在创建时已经完成

`BoundedEventQueue` 初始化：

```csharp
private TaskCompletionSource _completion = NewCompletion(null);
```

而 `NewCompletion(null)` 会立即 `SetResult()`。因此队列刚创建、仍可继续写入时，`Reader.Completion` 就已经完成；后面关闭又替换成另一个任务。

这与 `ChannelReader<T>.Completion` 的含义不一致：它应在**不再有未来可读取数据**时完成。（微软学习：System.Threading.Channels.ChannelReader-1）

最小修复：保留同一个未完成的 TCS，写端关闭并且 backlog 排空后才完成或失败。先修语义，不需要为此重建整个客户端队列框架。

### 3. 宿主"取消全部连接"与"确认连接结束"仍混在一起

`LiveStreams.cancel_all` 先清空登记表再调用取消 hook，后面 `wait_empty` 又用这张表判断是否已经退出。**表已被清空，不代表 worker、forwarder 和会话释放都已完成。**

同时，主程序仍主要等待 Ctrl-C，服务线程提前失败没有及时收敛；`composed.shutdown().await?` 失败时，也可能跳过后续传输停止步骤。

应保持：

```text
发出停止请求
  ≠ worker 已退出
  ≠ grant 已释放
  ≠ 宿主已完成关闭
```

取消时不提前删除 owner，确认完成时再删除；超时留下明确未确认结果。

另有一项较小的协议问题：`retyped` 在验证前把请求的 `work` 字段清成 `None`，可能把本来应拒绝的 run-scoped 信封"清洗"为合法请求。应验证原始信封或保留字段交给既有 validator。**这不是权限提升结论，会话授权仍由宿主安装。**

## 五、正式 GUI 仍有明确的待交付项，不应继续被基础研究挤掉

（按基线 `bbf7f5d` 时点描述；基线后 `9fb2030`/`433d21e`/`843803f` 已处理其中事件消费、审批详情与稳定行，验收以 N4 工单为准。）

## 六、当前 Windows 红 CI，应该修测试机制，而不是放宽阈值

失败测试：

```text
tests::admit::admit_store_read_does_not_block_unrelated_context_work
```

远端日志中的断言数据是：

```text
diagnostics 1.9093 ms
admit       1.5105 ms
```

这个测试试图用 32 MiB 输入制造慢读取，但输入经过默认 Context 正文裁剪，并不保证最后真的有一个慢 I/O；最终又用"admit 耗时必须大于 diagnostics 的三倍"推断没有持锁。

**这次失败不能直接证明生产代码持锁跨 I/O。反过来，偶然跑绿也不能稳定证明没有持锁。**

建议改为确定性屏障：

```text
确认 store read 已进入
  → 暂停这个读取
  → 验证 diagnostics 可以完成
  → 放行读取
  → 验证准入结果
```

超时只保留为死锁兜底，不再依赖相对耗时。这个修复可以随 A 线完成，不需要重新扩充整套评测框架。

（入库补记：基线后 `7e026ee` 已把该断言改为比例式并声明修准 load-flaky；确定性屏障方案仍为 A 线建议项。）

## 七、核心资产下一版本：算法与调度如何匹配

以下是设计建议，**本轮没有运行算法性能对照，不宣称已测得收益**。

### 1. Context：先做准确的证据装配，再做更复杂评分

建议使用：**硬约束与必要证据先处理；剩余材料按依赖组的"新增收益／新增渲染 token"选择。**

收益可以来自当前动作、未解决问题、来源覆盖与新增信息，重复内容则扣分。关键行为比公式更重要：**同一真实片段不重复收费；必要依赖一起计费；未用预算预留可借回；源本身 partial 时不能假装 required 已完整满足。**

当前任务焦点可以复用 `next_action`、open loops 和近期可信资源触达。它们只用于选择可选材料，**不能代替用户目标、权限或完成权威**。

### 2. 搜索：已有索引，不需要先加向量库

当前 `ContextCatalog` 已具备精确 ID、结构过滤、词法索引、正文前缀及残差检查。raw Tool／File 正文主要通过身份定位再 Fetch，也是当前明确的边界。

优先优化两件事：**一是减少重复计算**（查询预处理一次，条目 token／signature 复用）；**二是让候选相关性真正进入最终排序**（不能在倒排阶段算了更好的匹配，最后仍主要按访问时间排序）。先贯通现有词覆盖、字段和路径特征，再决定是否需要 BM25 的额外统计。

当前 Stored 残差读取已有最多 256 次读取、8 路并发和显式超限处理；**不是无界全库搜索，也不是默默假装完整。**先测冷读次数、真实 I/O 字节、延迟和相关性，再决定是否增加可重建的分段词法索引。

### 3. GC：保留现有增量基础，补 ownership 和恢复根

不需要重新发明增量 GC。下一步应是：**脏对象优先＋现有游标兜底；明确每次维护的对象、字节和等待预算；保证取消和 I/O 失败后的所有权。**

同时始终分开：

```text
语义是否有效
当前是否值得占用注意力
正文现在放在哪里
哪些恢复点仍要求保存它
```

缓存热度只能影响可逆驻留，不能决定用户约束或验证事实的真假。SIEVE／TinyLFU 等仍可作为以后正文缓存的候选，但不能成为本阶段默认前置。

### 4. 调度：唯一提交者，不新增第二个 Scheduler

继续让原 Actor 决定状态提交。异步维护返回任务、代际和资源版本，提交时重新核验。

控制面取消／撤销优先，但已经进入必要提交阶段的工作必须有明确收尾；必需证据与验证先于可选摘要和预取。**释放 state lock 只解决一部分问题，`op_gate` 或 Actor 仍在等待时，整体控制响应可能继续受影响。**

这应通过具体操作预算和取消边界逐步解决，而不是把所有调用都 `spawn` 出去。

## 八、下一阶段的三个并行任务

### A：上下文、GC、搜索

主要拥有 `context-simple`、`context-baselines`，分四个小切片：

| 切片 | 交付 |
| -- | --- |
| A1 | 持久归属、GC 取消、隔离失败、拒绝准入无副作用 |
| A2 | 片段范围、partial、required、最终曝光一致 |
| A3 | Rolling 摘要连续性、默认 profile 恢复、显式准入使用期 |
| A4 | 查询预处理、最终排序、边际预算装配、维护成本优化 |

**用户结果：**长期任务中的旧线索能找回，第二次压缩不会无意抹掉前次摘要，GC 不把 RAM 迁移误当持久保存。

### B：Runtime 与平台一致性

主要拥有宿主、应用路由、必要共享 DTO 和 .NET 客户端库。

| 切片 | 交付 |
| -- | --- |
| B1 | 快照／订阅同切点，live 与 durable 分流，重连代际 |
| B2 | 队列 Completion、真实关闭确认、服务失败收口、信封验证 |
| B3 | 给 GUI 提供真实任务、审批详情、结果／工件、只读 Context 接口 |
| B4 | 同一正式宿主 profile，多入口复用，已有 MCP／Skill 配置接入 |

**用户结果：**重连不会遗漏中间状态；坏连接与退出有明确结局；不同入口调用同一套应用行为，而不是各自拼 Runtime 内部命令。

### C：正式原生桌面与产品交付

主要拥有现有 Avalonia 应用、界面生命周期及发布整合。

| 切片 | 交付 |
| -- | --- |
| C1 | 真实事件消费者、模型／工具输出、真实计划和状态 |
| C2 | 知情审批、稳定行对象、单次刷新、连接代际和关闭清理 |
| C3 | 修改审阅、正式冷恢复、工件按需读取、只读 Context 检查 |
| C4 | 长会话资源上界、准确测量、Rust＋.NET 来源绑定包 |

**用户结果：**正式客户端能够提交、观察、审批、继续、恢复和审阅，不依赖布局夹具，不再增加准备淘汰的 GUI。

### 并行与依赖如何控制

**第一批就是 A1、B1、C1 同时开始。**每条线内部按小切片串行推进，不再拆成更多互相竞争的主工作线。

共享 `agent-contracts`、`agent-platform-protocol`、`RuntimeCommand` 和 compose 入口，由 **B 的负责人统一合入**；A 提证据／恢复字段需求，C 提界面实际需求。不是三条线分别发明 DTO。

C 的事件消费与对象生命周期不需要等 A 的全部算法实验；但**冷恢复、证据完整性等正式支持声明，必须等对应 A／B 回归通过**。

现有 N4、N5 的结果半、N7、N8 直接映射进这三条线，**不是在它们之前再加一整套大阶段前置任务**。

## 九、文档与执行方式也要一起收敛

当前任务文档已经有很好的范围意识，但同一文件里仍有"表格已关闭、下文还按旧问题写当前步骤"的叠加；开头的绿色 CI 也是特定历史 run，不应被读取成任何最新 SHA 都绿色。

建议只改现有活动入口：**CURRENT 写当前事实与限制；NEXT_TASKS 只保留这三线的当前切片；ROADMAP 写阶段目标。**旧问题的原始报告和证据继续保留，不重写历史。

你提供的历史审查材料中，Chronicle→TaskGraph→worker 是当时的阶段提案；这次不把它重新设成平台、GUI 或工具子 Agent 的强制前置，也不把本项目重新定位为 ContextCore 的子项目。

每个切片的回执只需要准确回答：**改了什么；接进了哪个真实用户动作；实际跑了什么；还有什么没验证；下一步是什么。**

没有新代码或新失败原因，不反复跑同一组长测试。没有 live provider 条件就把该场景写成 `NOT_RUN`，不能拿它阻止所有确定性功能交付，也不能因此把整个产品写成已经验收。

## 最后的优先级判断

**本轮最值得先处理的是三个问题：A 线的持久证据归属，B 线的快照／事件一致切点，C 线的真实事件消费。**

它们分别回答：

> **资料还在不在；客户端看到的是不是同一段事实；用户能不能实际使用这些能力。**

这三件事应当同时推进。先把它们做到可靠，再在同一条 A 线上逐步改进检索、装配和维护策略。这样既能保住上下文、GC、搜索作为核心资产的价值，也不会再让基础研究无限期占据整个产品主线。

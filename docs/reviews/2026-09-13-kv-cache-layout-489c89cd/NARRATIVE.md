**你这里说的缓存，应当明确包含供应商端的 KV／Prompt Cache，而且它需要直接参与上下文布局设计，不能只作为本地正文缓存的附属优化。**

这轮继续看下来，我的判断是：**保留 `CurrentStateLast` 的方向，但下一步要从“当前状态后置”推进到“稳定前缀分层、易变内容隔离、缓存写入策略明确”。** 当前实现已经有供应商显式缓存接入，不过它划定的复用区域仍然包含不少易变内容；在部分供应商的缓存规则下，这会削弱复用，甚至增加不必要的写入费用。

后端长流程优先、GUI 暂缓的安排不变。**KV 缓存布局应当与主体建设同步完成，而不是等 Context／GC 全部完成后再补。**

## 二、最重要的问题：现在的“可复用前缀”，还不是真正稳定的前缀

### 1. 唯一断点放在整个 `context_frame` 后面，范围太粗

当前 `ModelInput::into_request` 在 `CurrentStateLast` 下，计算的是：

```text
复用前缀消息数 = system_policy 消息数 + 全部 context_frame 消息数
```

而 `PromptAssembler` 实际拼出来的顺序是：

```text
system_policy
CURRENT FOREGROUND EVIDENCE       ← 本轮明确需要的前景正文
SELECTED WORKING CONTEXT          ← 选中的历史上下文
required_misses                  ← 当前缺失状态
EXTERNAL CONTEXT                  ← 外置引用及 residency 等字段
RESTORED TURN BODIES              ← checkpoint 后恢复的正文
──────── 当前唯一复用边界 ────────
turn_frame
current_state_frame
focus_frame
```

**问题不在“断点有没有发送”，而在断点之前混进了多少会变化的内容。** 新检索正文、缺失提示、外置条目状态、恢复正文，都在这个唯一边界以内。尤其 Foreground 在选中历史正文之前，前景内容一变，后面即使有很长的相同正文，也不再构成从请求起点连续相同的前缀。

例如：

```text
第 N 次：   稳定策略 + 稳定证据 + 缺失提示 A | 断点
第 N+1 次： 稳定策略 + 稳定证据 + 缺失提示 B | 断点
```

两次拥有相同的“稳定策略＋稳定证据”，**但当前实现没有在这个较早位置建立独立断点**。对于依赖已写入断点前缀的端点，不能仅凭存在相同文字，就推断它一定能复用那一段。

这应该是本轮布局优化的第一重点：

> **不要把整个 `context_frame` 当成一个稳定缓存块；要按内容的实际变化频率划定复用边界。**

### 2. 正文前的状态字段，也在破坏稳定性

`render_selected_item` 仍会把以下内容放在正文之前：

```text
workspace_identity=current
attention=...
semantic=...
```

同时，正文会根据是否已在协议尾中出现而被省略；之后又可能进入 `RESTORED TURN BODIES`。因此，**同一份文件、同一个版本、同一个范围的正文，仍可能因状态投影或跨层去重而改变前缀字节、位置甚至出现形式。**

这里要区分两种正确性：

**范围去重正确**，解决的是“模型到底看到了哪些正文”。

**缓存布局稳定**，解决的是“相同有效正文是否在连续请求中保持可复用的表示”。

前者修好，不代表后者自动成立。

建议把**仍然有效的证据正文及其来源身份**与**当前有效性、注意力、缺失等动态投影**分开组织。但有一个硬边界：文件确实改变、授权被撤销、用户要求移除或内容已不能作为当前事实时，必须及时失效，不能仅在尾部写一句说明，就继续把旧内容当作有效证据保留。

## 三、供应商接入还有两个具体缺口

### 1. 有显式断点，但没有 `prompt_cache_key`

当前 Responses mapper 已发送：

```text
prompt_cache_breakpoint
prompt_cache_options.mode = explicit
```

这是已有实现，应保留。但在实际 wire builder 中没有发送 `prompt_cache_key`。仓库里的 `PromptReuseBoundary.prefix_digest` 是前缀及工具的完整性绑定，**不是已经发送给供应商的路由键**。

按本次查到的 OpenAI 官方说明，GPT‑5.6 及后续家族采用断点前缀匹配，改进的匹配机制需要一致的 `prompt_cache_key`；没有键不等于绝对没有缓存命中，但不能获得相同的匹配行为。新家族的缓存写入还单独按普通输入价的 1.25 倍计费。**这不能直接推广到所有旧模型或 OpenAI-compatible 网关。**([OpenAI Developers][1])

建议在**已确认支持的端点配置**中增加稳定路由键，而不是把它塞成一个每轮变化的请求摘要。

我的建议是按安全隔离域、工作区／任务、端点配置和调用用途生成不透明键。同一任务的连续调用保持稳定，主执行与维护压缩可以分开。不要使用每轮 UUID、`model_round` 或完整动态请求的 hash。

**路由键负责让相关请求更容易找到同一缓存；内容摘要负责证明本次前缀仍然匹配。两者不能混为一谈。**

### 2. 选择显式模式，不代表所有调用都遵循“仅显式缓存”

当前 mapper 只有在有效 `boundary_index` 存在时，才写入 `prompt_cache_options`。缺少边界或边界过期时，请求会恢复成供应商默认模式；现有测试也明确固定了这个行为。

这还有一个实际调用方：

**Compactor 直接构造 `ModelRequest`，没有绑定复用边界。** 因此，即使它使用启用了显式缓存的 transport，也会走上述默认分支。

现在的配置更接近：

> 有合法提示时，加显式断点。

它还不是：

> 这类调用只允许缓存明确选中的可复用部分。

对于已确认支持 explicit-only 的端点，我建议明确区分：

| 情况          | 建议行为                     |
| ----------- | ------------------------ |
| 有合法、值得缓存的前缀 | 映射显式边界                   |
| 没有值得缓存的前缀   | 使用该端点支持的“不写缓存”方式         |
| hint 过期或不合法 | 放弃该 hint，并报告原因；不悄悄改变写入策略 |
| 端点能力未知      | 保持兼容默认，不发送未经确认的专属字段      |

OpenAI 当前说明中，explicit 模式没有任何显式断点时不进行 prompt caching，也不产生缓存写入费用；这提供了一个可用实现路径，但必须限定到已确认支持的端点。([OpenAI Developers][1])

**不需要每次压缩都缓存。** 压缩输入往往会变化，是否值得写入，应按实际复用机会判断，而不是因为主模型启用了缓存就一并开启。

## 四、不能用一套缓存假设覆盖所有供应商

这部分只影响能力边界，不要求现在把所有原生适配器都做出来。

| 供应商机制               | 对本项目布局的直接影响                                                 |
| ------------------- | ----------------------------------------------------------- |
| **OpenAI 的新断点机制**   | 不能只计算未标记的最长公共前缀；稳定内容需要对应的有效边界和接入配置                          |
| **Claude 前缀缓存**     | 缓存覆盖累积前缀，工具定义也在其中；写入与读取分开计费，末端易变块可能让较早相同内容无法命中已有缓存          |
| **DeepSeek 当前磁盘缓存** | 命中要求完整匹配已持久化的前缀单元；公共前缀可能需要多次请求才单独形成缓存                       |
| **Gemini**          | 隐式缓存与显式 `CachedContent` 资源不同，API 家族支持也不同，不能套用 Responses 的字段 |

这些差异来自本次核对的官方文档。([OpenAI Developers][1])

它们对架构有一个共同要求：

> **客户端负责组织可复用的有效前缀，供应商适配层负责把它映射为端点支持的缓存行为；实际命中和费用仍以端点报告及实际计费规则核对。**

给每个正文块加 hash，并不等于供应商能够独立复用任意块。对于前缀型缓存，原请求是 `A → B → C`，删掉 B 后变成 `A → C`，不能直接假定旧 C 的 KV 可以搬过来继续用。

这正是 GC、压缩与供应商缓存需要一起设计的原因。

## 五、我建议的落地布局：先保护稳定证据，再评估协议尾复用

### 第一片：先把稳定基座做好，不扩大协议改造

建议结构：

```text
稳定 policy / 稳定 runtime facts
    └─ 较早复用边界 B0：达到端点条件时启用

本阶段仍有效、预计重复使用的证据
    └─ 证据复用边界 B1

本轮新检索证据、缺失提示、临时恢复投影
完整协议窗口
最新任务进度、当前指令与焦点
```

这里最重要的不是多加几个字段，而是**不要在 B0／B1 之前插入每轮变化的东西**。

稳定证据也不应简单等于“历史全部内容”。正在反复修改的文件正文，可能更适合暂时留在易变区域；共享约束、相对稳定的依赖代码、当前阶段反复需要的有效材料，才更适合作为基座。

这一步可以沿用现有 `ModelInput`、复用摘要、最终 packing 和 provider mapper，不需要另造一个上下文系统。

### 第二片：引入有界的阶段稳定性，而不是退回无限追加历史

进一步优化时，可以让一个小阶段内的有效证据快照和必要协议组保持稳定，新增结果在后面追加；到任务阶段切换、必要证据大幅变化或预算边界时，再重建。

我这里说的阶段，指的是**有界的请求布局生命周期**，不是新调度器或新任务数据库：

* 当前 TaskAnchor、Context owner 和工具权限仍然是唯一权威。
* 布局只保存有上限的派生视图，其持有的正文也计入真实内存预算。
* 必需证据更新、权限撤销、用户纠正和硬预算可以立即触发重建。

这样才不会出现“Context 已经 GC，但另一份 prompt snapshot 又把所有历史永久留住”的问题。

### 协议尾缓存应当另做一片，不能顺手扩大

当前复用边界只接受 System／User 消息前缀，没有把 assistant／tool 协议纳入；checkpoint 的动态说明和滚动保留窗口也会改变这部分内容。**这是后续优化空间，不应当直接当作当前协议错误。**

第一版先保护稳定证据基座。后续确实要复用协议段时，再按供应商支持的位置映射断点，并保持完整的 call／result 配对和真实角色。不能为了缓存，把工具返回改写成普通 user 文本，也不能随意解除现有边界验证。

### 工具表面已经排序，不要重复优化错地方

`RoundSurfacePlan` 已经对最终工具按名称排序。现在需要关注的是**工具集合是否因加载、需求或预算发生不必要的变化**，不是再加一遍排序。

可以减少无业务意义的集合抖动，但真正的工具撤销、不可用和安全策略变化必须立即生效。为了保住缓存而保留旧 schema，不是可接受的优化。

## 六、为什么“压缩后 Token 更少”不一定马上更便宜

这一点会直接改变 GC／压缩策略的评价方式。

假设只是为了比较策略，令普通输入每 token 成本为 1，缓存读取为 0.1，缓存写入为 1.25。已有一个命中的 **10,000-token** 基座，考虑压成 **8,000 token**；再假设新基座需要全量重写，未来 \(K\) 次请求都稳定命中，暂不计压缩调用和输出差异：

$$
C_{\text{保留}} = 1000K
$$

$$
C_{\text{重建}} = 8000\times1.25 + 800(K-1)
=800K+9200
$$

在这个**纯假设例子**中，未来只有 10 次请求时，保留成本是 10,000，立即重建是 17,200；到 46 次才持平。

**这不是某个模型的实际报价，也不是建议固定 47 轮再压缩。** 较早断点仍能命中、只需要重写小后缀、TTL 过期、输出变化和压缩费用，都会改变结果。

它说明的只是：

> **减少输入长度、减少未缓存输入、减少缓存写入，是三个不同的目标。不能仅凭输入变短就宣布降本。**

因此建议记录的任务成本是：

$$
C_{\text{任务}}
=
\sum_{\text{主调用、维护调用的每次真实尝试}}
\left(
p_uU+p_rR+\sum_j p_{w,j}W_j+p_oO
\right)
+
C_{\text{存储}}
+
C_{\text{工具}}
$$

其中普通输入、缓存读、不同写入桶必须按供应商口径正规化。原始 usage 要保留，不能统一套用 `input - read - write`，也不能把缺测补成零。

### 当前重试账目还需要补全

本轮重新核对到：重试层暂存的是**最近一次失败 usage**；成功分支返回成功 output，没有合并此前已知失败用量。等待重试时取消，以及部分 sink 错误出口，也会直接返回错误。

这会影响缓存优化的评价：失败请求可能已经发生计算或缓存写入，只看最后一次成功调用会漏掉成本。

建议复用现有调用标识和事件道，结算每次真实 attempt 的已知用量与完整性。**同一次尝试的多个累计 SSE 快照不能重复相加，不同真实尝试的已知成本则不能丢。**

现有 `diagnostics.rs` 已经提供最终请求、input item、tools、settings 摘要和读／写／miss 观察字段，而且正确注明“字节前缀不是服务端 token 命中”。应当扩展这些现有设施，不再建设平行的缓存观测框架。

## 七、其他主线上的两件事不能被缓存工作盖过去

### 搜索续跑漏了模型可见参数

现在 `GrepArgs` 和执行分支已经支持 `scan_continuation`，描述也指导模型继续扫描，但 `SearchGrepTool::spec` 的 `input_schema.properties` 仍然只有：

```text
pattern
path
limit
```

**后端支持，不等于执行者 LLM 能稳定使用。** 这会造成工具描述、参数表面和执行器不一致；严格参数生成或校验可能进一步放大问题，但本轮没有实测某个供应商必然拒绝。

这是一个应先修的小闭环：声明参数，再验证经过 `compact_for_model_surface`、provider wire 和正式 dispatcher 后仍然能继续到第二批。不要只测直接调用 `execute`。

### 最新 CI 有清理边界失败，不能宣布主体已经稳定

该 SHA 的 CI 第一次运行中，Linux part 2 已失败，其他若干构建／测试作业成功，读取时 Windows 全量测试仍在运行。

我读取的失败日志定位到 `proof_supervision.rs`：宿主死亡后，测试未在期限内确认验证进程树退出，超时点仍报告确切进程身份为 Running。**根因尚未定位，不能直接说是生产必现缺陷，也不能先当作普通抖动跳过。** 这属于执行核心的清理与恢复边界，应与缓存工作并行处理。

## 八、下一步任务保持三线，但把供应商 KV 明确写进交付

| 主线                  | 本轮具体推进                                   | 停止条件                             |
| ------------------- | ---------------------------------------- | -------------------------------- |
| **A：执行核心与工具**       | 调查上述清理失败；补齐搜索续跑 schema；继续任务纠正、中断、恢复和验证闭环 | 正式入口能完成实际动作，未知效果不被盲目重放           |
| **B：Context／GC／搜索** | 稳定证据与易变投影分离；维持真实版本／范围／liveness；继续有界资源管理  | 必需证据正确可见，冷热往返可恢复，缓存不制造另一份无界历史    |
| **C：平台与供应商 KV**     | 稳定路由键、明确写策略、分层边界、失败尝试用量，之后再评估协议尾复用       | 最终 wire 正确，固定任务质量不下降，成本变化有读写账目解释 |

最先落地的缓存切片，我建议是：

**稳定路由键与 explicit-only 策略 → 稳定证据基座边界 → 去除无意义的前缀变化 → 用现有固定任务验证总成本。**

验证要包含连续请求中的真实变化：新增检索正文、缺失提示改变、checkpoint 恢复、文件修改、工具撤销，以及失败后重试。只验证“换一句 Focus，前面字符串没变”，不足以代表真实长流程。

**最终结论：你的补充是必要的。当前要优化的不是一个孤立的“缓存模块”，而是 Context／GC 如何产生适合供应商复用的请求序列。主体建设仍优先，但“稳定有效前缀、受控写入和完整成本账目”本身就是主体的一部分。**

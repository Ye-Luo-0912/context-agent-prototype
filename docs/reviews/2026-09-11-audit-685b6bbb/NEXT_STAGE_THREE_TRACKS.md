# 下一大阶段任务书：可靠长任务工作台

## 0. 基线、范围与执行约定

基线仓库：`Ye-Luo-0912/context-agent-prototype`，提交 `685b6bbb29275bc8ec73ce6625a94567a8b8d23d`。

本任务书对应 `AUDIT_685b6bbb.md` 中的源码发现，不表示仓库原有 N/W 任务未完成。CORE-*、PLATFORM-*、GUI-* 是本文建议标识，合入仓库时可映射到现有任务系统。开始开发前只需核对基线之后相关文件是否已改变；若问题已修，应引用实际修复和回归而不是重复实现。

本次审查没有执行本地 Rust/.NET 测试，实际读取范围见审查报告。任务书要求的验收是后续开发的完成条件，不是声称已经通过。

### 本阶段交付目标

用户能从正式桌面客户端连接真实宿主，提交一个跨文件任务；模型能够区分“看到了某个范围”和“文件身份已知”，使用完整性明确的检索结果；用户能够查看修改、完整产物和证据，并在追加指令、取消或重连以后继续同一个有明确身份的工作。

这是现有架构上的产品增量，不是重建 Agent，不是再做 GUI 验证壳。

### 权责不变

- RuntimeActor：唯一调度器，执行轮次、安全点、取消与恢复协调。
- TaskManager / TaskAnchor：任务身份、解释、约束与进度，继续属于 runtime。
- Core：授权、操作/效果权威与日志；不新增任务规划权威。
- ContextEngine：选择、驻留、可恢复外存与派生摘要；不自行撤销无法证明失效的用户约束。
- Platform：鉴权后的路由、连接和可查询结果；不创建另一个任务状态机。
- GUI：可信状态投影及显式用户操作；不以日志文字、同名目标或超时自行判定事实。

### 三条并行分支

| 分支 | 主要所有权 | 不自行修改的边界 |
|---|---|---|
| 核心 | `agent-runtime` 的执行/上下文/请求组装，`context-simple`、`context-baselines`，基础 fs/search 输出，provider 请求与 usage 语义 | 平台对外 DTO 的合并由共享接口负责人负责；不改 GUI |
| 平台 | `agent-host`、runtime 的平台路由，IPC/连接生命周期、对外读模型，.NET SDK 的协议与连接 | 不拥有 TaskManager；不改 GC 策略 |
| GUI | `apps/Agent.Desktop`，正式用户工作流、面板状态、导航和呈现 | 不直读宿主数据库/状态目录，不绕 SDK 推测完成/授权 |

`agent-contracts`、`agent-platform-protocol`、RuntimeCommand 的对外增量、`agent-compose` 以及共享 DTO fixture 由一名接口合并负责人协调。默认由平台线负责合并，但核心语义必须由核心线确认。不要三条分支各自发明版本不兼容的 Result/Receipt/ContextFrame。

## 1. 共享的小前置：明确已有契约需要增加的字段

不是独立大工程，也不能成为阻塞三条线开始的长期设计阶段。先提交一份短契约变更说明和共同反例 fixture，然后并行实现。

### S1.1：证据投影

在现有 `FileBodyWindow`、ContextHints、MaterializedContext 和输出 DTO 上补足需要的信息。具体命名服从现有类型：

```text
resource identity: workspace/run binding + normalized path + content revision
visible extent: line/byte interval, or verified whole-file
completeness: full / partial / unknown, clipping or scan-limitation reason
provenance: call/item/artifact identity, when available
```

**同版本 ≠ 同范围；范围声明 ≠ 截断后仍完整。**

本轮“最终可见清单”是最终请求的派生视图，不是新持久化任务权威。完整值过大时保留可恢复引用和明确缺失，不伪装已经显示。

### S1.2：请求结果身份

为现有提交收据增加可查询路径，明确进程内与跨重启承诺。使用已有 run / epoch / client_request_id / task_id / payload 身份，不通过 goal 文本匹配。

最小结果分类：accepted、known rejected、unknown、expired。unknown 与 expired 都不能自动变成“未执行”，也不能自动重发。

### S1.3：可读完的产物

在既有 sealed artifact 身份上增加 offset/cursor、next offset、eof/partial 状态；保持每页硬上限与权限/内容摘要核对。不要新建任意路径下载接口。

## 2. 核心线

### CORE-1：修复正文覆盖真值（先做，F01）

**用户可见结果**：模型不再因读取同文件另一个片段，丢失之前需要的片段；重复信息确实存在时仍能省略。

**实现落点**：

`execution/body_cache.rs`、`actor/mod.rs::record_protocol_body`、`prompt.rs`、`actor/model.rs`、`context-simple/materializer.rs`，以及 broker/runtime 的二次限幅边界。

**实施顺序**：

1. 正文缓存保存原始范围、修订、完整性及来源，不再只用 `(path@digest, body)` 表达覆盖。
2. 对尾部保留、checkpoint 回注、外部补读采用同一套范围联合计算；只有实际进入本轮请求的正文参与覆盖。
3. 在预算裁剪和 schema 裁剪之后重新确认最终可见集合；必需正文被移除必须进入 required misses。
4. head/tail 限幅降级覆盖声明；未知范围、越界空读、不同版本均不能升级 whole-file。
5. 缓存容量策略保持现状起步；先修正确性，再按真实复用情况决定是否保留多片段/合并邻接区间。

**最小验收**：同版本不相交片段；相邻区间联合覆盖；不同版本；缓存中存在但本轮未回注；broker 截断；缓存淘汰与跨尾部截断。正例必须证明确有重复时仍能去重。断言检查实际 `ModelRequest`，不只看 ContextHints 或缓存内部状态。

**停止条件**：上述路径能保持真实覆盖即可，不借机重写 GC 或添加新存储后端。

### CORE-2：公共上下文义务与保守语义终结（F02、F03）

**用户可见结果**：任务的强制依据不会静默丢失；改变一项要求不会顺便抹去同文件其他要求。

**实现落点**：基线上下文引擎、ContextEngine 能力边界、请求最终检查、`engine.rs` 摄入与 `gc/reachability.rs` 的决策 supersession。

**工作**：

- 选择公共 mandatory-claims 实现，或明确的能力声明/Unsupported 结果。不要用空 required misses 表达未支持。
- 保持 append/rolling/dynamic 的实验选择策略差异，但为生产任务定义相同的最低正确性边界。
- 决策终结必须指向具体旧决策及替换依据；文件实体重叠只用于检索/相关性，不直接触发永久语义撤销。
- 不确定关系保持 Live 或仅改变注意力。已有精确文件版本替代与同 probe 错误修复保持不变。

**最小验收**：各生产策略遇到同一个 required item 都必须呈现它或明确报告不能满足；旧 timeout + 新 logging 替换应并存；显式撤销指定旧决策应成功；跨任务相同文件不互相撤销。

**停止条件**：不增加大型语义解析体系，不调整全局打分权重，不把已有 W04 取消重做成新里程碑。

### CORE-3：把检索、补读和恢复串成真实可用的工作流（F04）

**用户可见结果**：模型知道搜索是否找全，能定位并补读具体范围，而不是不断全仓重扫或把扫描受限误当没有更多结果。

**工作**：

- fs/search/context/artifact 的模型正文采用一致的来源与完整性表达；summary、metadata、原始 artifact 和正文不得互相矛盾。
- 有命中与无命中都必须表达 scan completeness；结果分页保留查询/范围身份和结束标记。
- 已存在的目录、索引、context lookup 和 artifact paging 直接复用。先统一结果契约，不新建重复索引。
- 待真实任务证明遍历是瓶颈后，再做路径/版本驱动的增量索引。不可把跨工作区、跨版本负结果当成有效缓存。
- 工具 schema 的选择仍基于 runtime 已有 surface/lease 机制，不为提高缓存命中率把全部工具永久塞进 prompt。

**最小验收**：一个命中文件加一个被跳过文件，最终模型请求必须带不完整状态；能继续有界补读；外部文件更新后旧证据要失效或明确历史身份。

### CORE-4：以总任务成本优化缓存，而不是只优化缓存率

**用户可见结果**：长任务少重复读取、较少无效压缩，并能解释成本来自哪里。

**工作**：

- 保留 CurrentStateLast 和现有公共缓存边界，不重新安排“建立缓存布局”这种已完成任务。
- 稳定不变段保持顺序和序列化；当前焦点、最新指令、权限/工具 surface、有效性事实更新时立即反映，不为旧缓存冻结它们。
- 缓存配置继续以实际 provider capability/profile 为准；默认兼容路径不自动注入某一厂商的显式参数。
- 主请求、压缩、重试、取消统一记账，保留每次 usage 的 observed / estimated / unknown 身份。未知不是零，cache miss 不是 cache-write 计费证据。
- 压缩器的调用预算、输出限额和统计独立可见；先追踪真实 wire 参数再决定是否需要单独的 compaction provider profile。
- 在修复上述正确性后，用现有评测/验收入口比较端到端成本；不再建平行 benchmark 项目。

**验收**：任务成功/证据准确不退化；所有模型调用角色都有账目；提供同起点任务的缓存读写、压缩、重试、补读、总消耗对比。只给“命中率提高”不算交付。

## 3. 平台线

### PLATFORM-1：精确提交回执查询与重连后的未知状态（F06）

**用户可见结果**：断线后能区分这次提交已受理、明确失败、证据丢失或仍未知。

**实现落点**：现有 `WorkSubmissionRecord`、actor 查询命令、平台工作路由、协议与 .NET SDK；不新增第二个 TaskManager。

**工作**：

- 从现有进程内账本增加只读 exact-request 查询；请求 envelope 的 message id 与 client_request_id 不混用。
- 返回 epoch/run/request/payload 对齐的结果，不以 Goal 作幂等键替代 request id。
- 明确 256 条进程内窗口以外及重启后状态；证据不足继续 unknown/expired。
- 若产品要求跨重启确认受理，持久化必须与已有提交/检查点权威保持一致，设计 accepted 的提交点和恢复判定；不要先对用户承诺 exactly-once 再补证据。
- 改写重连核对文案和 SDK 类型，让 GUI 无须自行推理。

**验收**：旧同名任务存在但本次未受理；本次已受理而 ACK 丢失；去重窗口过期；宿主重启；同 id 不同 payload；用户显式选择重新提交。禁止无依据“成功”和无依据“肯定未执行”。

### PLATFORM-2：完整结果与证据读取（F08）

**用户可见结果**：能读完大型产物、从变化摘要定位实际内容，并看到信息的新鲜度/完整性。

**工作**：

- 扩展现有 artifact API 为有界分页读取，绑定原始 run 和 sealed digest，返回位置与 eof。
- 在现有 changes 读模型上补可定位的修订/产物引用；真正 diff 的正文读取复用工作区可信路径，不开放任意宿主文件。
- context 读模型区分“在存储中”“驻留”“这轮实际发给模型”“只是摘要/指针”；从现有事实派生，不另建持久化真值。
- 保持只读权限与预算、deadline，禁止通过读接口绕过原有副作用授权。

**验收**：大 artifact 尾部可读，跨页中文/UTF-8 正确，页身份不能换版，外 run/摘要不符被拒绝，读请求不启动模型也不改变任务状态。

### PLATFORM-3：正式宿主连接契约（支持 GUI-1）

**用户可见结果**：默认连接在目标操作系统正常工作；连接指向哪个工作区和宿主清晰可见。

**工作**：

- 将平台选择逻辑集中到 SDK/连接配置，RealHost 根据 OS 选 Named Pipe 或 UDS，兼容显式 endpoint。
- 定义统一 WorkspaceIdentity/endpoint 展示与解析规则，消除相对路径/绝对路径及客户端当前目录造成的歧义；先实现明确工作区选择/复制端点，不抢做多租户服务。
- 重连时公开 host/run epoch 和协商 profile；保留已有单用户隔离、grant 撤销、bounded frame、背压与 resync。
- 共享协议 fixture 检查 Rust 与 .NET 的关键字段、错误分类及 unknown/null；版本不兼容应明确拒绝。

**验收**：生产入口连接 Windows 与 Linux 支持目标；相同工作区解析一致；不同工作区不误连；断线后旧连接的结果不污染新会话。

### PLATFORM-4：让三条线使用同一份事实

维护共享接口版本与有限的一组跨层 fixture。保证核心的 evidence completeness 和 usage 来源可以被 SDK/GUI 原样读取。对已有指标与恢复事件做增量字段，不新建任务日志数据库。文档中的默认 provider、context policy、host endpoint 和真实配置保持一致。

**停止条件**：不另建评测平台，不把 MCP/Skills/多 Agent 的全面扩展放进本阶段阻塞链路；这些外围能力继续遵守现有接口边界。

## 4. GUI 线（沿用正式桌面工程）

### GUI-1：修复默认连接和异步结果隔离（F05、F07）

**工作**：

- 实际 ConnectAsync 走 PLATFORM-3 的平台感知选择，不只修测试工厂。
- 为所有只读请求统一捕获 connection epoch、selection id、request sequence；成功、失败和收尾均校验后才更新界面。
- 旧任务详情不能覆盖新选择；旧连接失败不能清掉新连接有效面板；断开/切换时清理所属 era 的 UI 缓冲。
- unknown、未送达、已受理、已执行、已完成用不同状态；超时/断线不是未送达证明。

**验收**：实际生产连接入口；A 慢 B 快的任务切换；旧连接错误晚到；重复连接/断开；默认 Linux 连接。不要仅用直接注入已连接 session 的测试代替连接选择验证。

### GUI-2：把已有只读面板推进为结果审阅工作台（F08）

**正式工作流**：任务选择 → 当前指令/约束/计划 → 变化 → diff 或产物 → 原始证据 → 继续工作。

**工作**：

- 保留已有任务、审批、changes、artifact、context 面板，不重新声明“从零搭建 GUI”。
- 对接 PLATFORM-2 分页，支持继续阅读和明确 eof；有限窗口/虚拟化，不把全文无限拼接进一个字符串。
- 提供文件/产物身份、修订、部分/完整标记；点击证据可回到对应调用或结果。
- 输出正文与运行日志分开呈现；日志不充当最终结果真值。恢复后的结果从平台可读事实获取，而不是重放终端文字猜出来。

**验收**：大结果的关键结论位于尾部时，用户仍可从 GUI 独立核查；重复查看不重新触发模型或工具副作用。

### GUI-3：可靠的继续、审批、取消、重连体验（F06）

**工作**：

- 使用 PLATFORM-1 的 exact request 查询；删除基于相同 Goal 消除未知提交的逻辑。
- 追加指令明确绑定选定 task；展示当前执行/等待/审批/停止/未知状态，不隐式启动另一个任务。
- 取消按钮先显示取消请求状态，只有可信确认后才显示停止；无法确定的副作用保持提示。
- 重连先取可信 snapshot，再按 watermark 接续事件；已有机制复用，不另起事件真值源。

**验收**：丢 ACK、重启、旧同名任务、审批响应未知、取消与工具完成竞态均无虚假确定文案，也不自动重发有副作用操作。

### GUI-4：显示模型真正拥有的信息和成本

**工作**：

- 任务视图中显示当前有效指令、仍未闭合的问题和所需证据，不将原始任务目标误作永久覆盖当前补充指令。
- 上下文面板区分 actual sent / resident / pointer-only / stale / missing；只展示来自核心/平台的事实。
- 成本显示主调用/压缩/重试，区分实际 usage、估算和未知。缓存读写与缓存命中率分开，不用未知零值给出“免费”印象。
- 随功能拆分 MainWindowViewModel 为 Connection/Task/Review/Approval/Usage 等小状态组件；不把大规模纯重构先设为全功能前置。

**验收**：用户能回答“为什么模型又读了一次这个文件”“哪些资料没有完整提供”“这次取消有没有未知费用”，而不必翻底层 JSONL。

| 波次 | 核心 | 平台 | GUI |

## 6. 统一阶段验收：一条真实用户旅程

复用仓库已有验证与回归入口，不额外建立独立任务编排或 benchmark 系统。

1. 从正式 GUI 默认连接真实宿主，提交跨文件修改任务。
2. 模型搜索到部分命中且遇到被跳过范围，明确看到不完整声明并补读。
3. 对同版本文件读取不相交片段，跨过尾部截断，再需要较早片段；它仍准确可见或可恢复。
4. 用户追加只改变日志格式的要求，原有超时/兼容性约束没有被撤销。
5. 过程中断线导致一个 ACK 丢失，重连不凭同名任务猜测，也不自动重复提交。
6. 用户从 GUI 阅读大型产物尾部和修改证据，触发一次显式取消/继续；所有状态与实际 authority 一致。
7. 完成后汇总任务结果与 observed/estimated/unknown 成本；丢失 usage 的取消不能显示成零消耗。

**通过条件**：任务产物正确、必需证据闭合、权限/副作用边界保持、默认生产入口可用、未知状态不被假定为确定、结果可完整核查。缓存优化不得以损失任何一项为代价。

## 7. 文档交付与停止规则

每条线提交实现、与新行为直接相关的最小回归、一个真实生产路径演示说明和必要文档增量。已完成任务引用旧验收，不复制成新清单。

`CURRENT` 只写实际默认配置、最近成功路径及未验收限制；`NEXT_TASKS` 保留三条当前主线与共享接口；历史任务归档但不删除必要证据。

本阶段不做：新 TaskGraph/Chronicle 权威、新向量数据库、新 GUI 验证壳、大规模无功能重构、仅为了命中率的全局上下文冻结、未经真实需求的全量多 Agent 平台。发现与本阶段无关的问题记录后继续当前用户可见交付，不因无限完善测试而停住主线。

## 1. 结论

下一阶段不是 Execution Chronicle 或 TaskGraph 平台，而是将已有 TaskAnchor、RuntimeHandle、RuntimeInstance、验证/权限、Context 与工具能力组织成一个可反复使用的产品闭环。

附件历史方案提出“可靠性与M15 → Chronicle → TaskGraph → worker”。这是该材料的提案，不是本轮实现事实。当前读取的代码已经有可复用的实例、任务进度、恢复与脚本模型集成。不能直接把旧文档中“缺少”的项目当作今天仍应从头建设的模块，也不能继承其中的历史跑测声明。

本阶段允许人类验收；不把“能够自动证明任意业务目标已完成”作为交付前提。产品应该准确说自己做到了哪里，而不是通过继续跑测试来争取一个不具备授权条件的完成标记。

## 2. 这次代码核对改变了什么

| 源码事实 | 对任务计划的影响 |
|---|---|
| `TaskCompletionPolicy` 默认 `OperatorClosureOnly` | 无宿主验收域的普通任务默认交付待审阅结果；不诱导模型反复调用必被拒绝的 task.complete |
| `next_action` 明确不是完成阻塞 | 不新增必须清空next_action的规则，也不把清单前缀当成验证 |

| `max_tool_rounds` 的执行条件实际上读 `turn.model_round` | 用户预算及日志统一使用实际计量单位；不是工具调用条数 |
| `RuntimeInstance` 已拥有跨平面恢复与有序shutdown | CLI/TUI复用完整实例入口，不重写恢复事务或第二个host生命周期 |
| `product_flow.rs` 用不同于TUI的配置，正常shutdown/restore且未continue | 增补一条真正产品配置下的恢复后执行流程；不把测试名字当已跑通功能的证据 |
| 已有 `crash_resume.rs` 真实硬退出和变更journal计数 | 复用已有fault harness，不另建泛化崩溃评测平台 |

## 3. 完整产品闭环

```text
用户任务/受控非交互输入
  → 参数、配置与权限预检
  → 现有RuntimeActor创建/激活Task
  → 工作模式按需启用task.manage
  → TaskAnchor短计划/open loops/next action
  → 有限模型决策与Core授权工具执行
  → Context检索、片段恢复、预算装配与最终曝光ACK
  → 正常产出 / 人工待审 / 可信完成 / 让出 / 取消 / 恢复受阻
  → 有界结果卡 + 已知修改归属 + 真实检查 + 安全检查点
  → 同Task显式继续或完整RuntimeInstance冷恢复
```

Task/Effect/Checkpoint保持原有权威归属；RunView/计划面板/结果卡只是投影。处理一条指令的host事件泵不是另一个工具编排器，不能自行决定下一模型/工具调用。

## 4. 功能交付顺序

- **交互闭环：M16-00～02。** 当前文档收敛、可信预检、继续/补充、短计划和完成模式。尽快独立交付。
- **可靠交付：M16-03～06。** 有限执行和取消、冷恢复、结果审阅、上下文/搜索正确性。按受影响能力分开提交，不扩大为全仓修复先行。
- **可调用产品：M16-07～08。** 同Runtime的headless入口、精确构建发布、三类真实使用记录。

具体实现入口、步骤、检查、退出条件和禁止扩展项只有一份权威队列：`replacements/docs/NEXT_TASKS.md`。TASKS.json只是该队列的同源机器表示，不是新的运行系统。

## 6. 核心资产的本阶段与下阶段

### 本阶段必须闭合

- **Context：**保持原始用户约束、当前子目标与可恢复正文分开；ResourceVersion与EvidenceSlice分开；实际最终发送的内容驱动消费确认。
- **GC：**attention、semantic、residency正交；有效保留义务跨tier一致；可逆外置不冒充语义失效；共享实体不是可信修复证明。
- **搜索：**精确身份可定位、候选生成不过早丢掉新材料、恢复不自动准入；分页剩余与扫描覆盖分开，raw文件搜索和语义记忆搜索不混同。
- **调度：**继续单Actor提交，复用有界operation；修慢等待、取消和I/O责任；不要以删锁或随处spawn代替版本验证与提交边界。

### 有数据才进入的算法候选

| 已观察问题 | 候选 | 最小实现 | 衡量 | 不应声称 |
|---|---|---|---|---|
| 搜到很多材料但前排偏离当前目标 | 字段化BM25式词法排序 | 先将现有coverage/rarity传至最终排序，再决定tf/长度统计 | 冻结小查询集命中、需要追加查询次数、IO成本 | 换公式必然提升任务成功率 |
| 冗长/重复条目挤掉有用材料 | 依赖组边际收益/新增token | 判重、硬根先行、实际依赖计费、预算借回 | required miss、实际输入成本、任务修复回合 | 已获得最优背包保证 |
| 可逆正文恢复频繁且昂贵 | SIEVE候选；准入污染再看TinyLFU | 只替换可选正文缓存，保持可靠外置 | 恢复字节/延迟、抖动与内存 | Web缓存论文能证明Agent记忆正确 |
| 安全点扫描占用明显 | 脏对象队列+已有游标兜底 | 先复用已有批次，必要时到期堆 | 维护时延、最大陈旧窗口、前台响应 | 仅释放state锁就没有阻塞 |
| 摘要成本高或伤当前焦点 | 精确可恢复的旧观察遮罩 | 先留原文，再指针化；关闭阶段才局部摘要 | 包括摘要、恢复、重试在内的总任务成本 | 摘要越短效果越好 |

这些是工程假说；本轮没有运行它们的对照，也没有重新开展论文研究。M16不以任何一个新算法胜出为前置。阶段末根据实际数据只选择一个后续工作包，未出现瓶颈就保留简单实现。

## 7. 文档要减什么

AGENTS/CURRENT/NEXT_TASKS/ROADMAP维持一个活动方向；STATUS只作短索引。旧M15候选路线、已闭合门禁和冗长审计不再默认加载，但原始报告、用例和契约保留。

不新建RUN_RECORD_SCHEMA、LONG_FLOW_V0、Chronicle数据库设计等作为当前前置。若产出新协议，更新对应现有契约文档；普通UI接线不要求同时重写全部架构文档。

活动状态要区分“实现了”“测试了”“默认启用”“真实用过”。旧source的CI与冻结evidence只证明其原对象；不能默认覆盖新提交。源码中的旧冻结注释应解释为实验可比性约束，不是永久禁止修正确性问题。

## 8. 发布结束条件

产品能在其声明的平台/默认配置下完成三类实际任务记录，并能明确待审阅、已持久完成、预算让出、取消或恢复受阻；不会靠静默数据丢失/重复副作用制造成功。构建来源准确，用户未提交修改被保留，受影响的已知权限/持久性/资源边界问题已处理。

真实provider不可用时可以交付“确定性接线完成、真实走查NOT_RUN”的版本，但不能把整个阶段的真实使用验收标PASS。也不能以缺服务为由倒退重建所有基础设施。

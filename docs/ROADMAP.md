# 产品功能路线

> 状态：当前交付顺序。自本次路线调整起，旧报告及旧 TODO 中的“先全部可靠性收口、再重新评测、再开发功能”不再作为通用前置条件。
> 不改变 Core 安全边界，不改写历史实验结果，不取消现有 CI。

## 目标与边界

交付一个可日常使用的本地 Coding Agent：用户给一个仓库任务，Agent 能查看代码、维护简短清单、修改与检查、响应补充输入、被中断后继续，并给出可审阅结果。

当前产品范围仍是单用户、一个工作区、单 RuntimeActor、内建工具、动态进程内 Context 和 TUI。
长期任务采用现有串行工具循环与 TaskAnchor，不先建设执行图、数据库或平台。

已经发布的 v0.1.0、已有 M15/LT-EVAL 记录、doctor、检查点和状态投影是基础，不再作为待重做事项。
“已有代码”“默认产品启用”“实测可用”分别记录，不再用前者代替后两者。

## 测试如何配合主线

测试服务于正在交付的功能，不再以测试数量和重新开窗次数计进展。
开发循环用定向测试和短演示；集成复用现有跨平台 CI；触及持久化、effect 或权限时保留对应已有回归。
旧失败不掩盖，新回归不放行；与本功能无关的历史边角问题不自动升级为所有功能的前置条件。

研究轨与产品轨分开。冻结实验用于研究结论；正常产品迭代不需要每次重跑完整 M15 或 LT-EVAL。
三个真实任务是产品走查，不替代科学比较，也不把未跑写成通过。

## 核心资产的近期处理

- Context：先保证当前任务、清单和实际证据片段能稳定进入请求；不立即翻转 shadow Frame 为正式 prompt。
- GC：保留可逆外置、驻留/语义分离与已有策略；已确认缺陷可定向修复，不展开 SIEVE/TinyLFU 调参项目。
- 搜索：先保证路径/片段可定位、截断和未扫描范围可见；暂不接 BM25 新后端、向量库或学习排序。
- 调度：继续由单 Actor 处理；耗时验证复用现有异步路径，不建设第二调度器。

## 后续候选，不是当前承诺

日常 TUI 流程形成后，下一项优先考虑复用现有组合的非交互入口，便于脚本与编辑器调用。
更好的代码/历史检索、Context 算法、编辑器接入按真实使用记录分别选题。
Chronicle、结构化 TaskGraph、多 Agent、worker、MCP/插件生态扩展和递归改进不进入本轮队列。
需要这些能力时先指出现有简单路径解决不了的具体用户任务，再决定最小扩展；不把它们互相设为依赖。
